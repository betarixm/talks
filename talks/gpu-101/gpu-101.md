## 1. 시작은 “게임 화면을 제시간에 그려라”였어

게임 속에서 햇빛이 비치는 호숫가를 걷고 있다고 해보자. 카메라가 움직일 때마다 물결의 모양도, 나무가 가리는 부분도, 수면에 비치는 빛도 달라져야 해.

컴퓨터가 가진 것은 나무와 수면을 나타내는 **삼각형들, 재질, 조명, 카메라 위치**야. 이것을 가지고 화면의 각 위치에 어떤 색을 표시할지 계산해야 해. 이 작업이 **렌더링**이고, GPU는 원래 이런 3D 그래픽을 빠르게 처리하기 위해 발전한 장치야. 

그런데 화면에는 픽셀이 엄청나게 많아. 가령 약 200만 픽셀짜리 화면을 초당 60장씩 만들어야 한다면, 매초 1억 개가 넘는 출력 픽셀의 색을 만들어야 하지.

여기서 눈여겨볼 점은 단순히 “계산이 많다”가 아니야.

**서로 다른 위치에 대해, 비슷한 계산을 엄청나게 많이 한다는 것**이야.

수면의 이 지점에서도 빛의 반사를 계산하고, 바로 옆 지점에서도 빛의 반사를 계산해. 들어가는 위치와 방향은 다르지만, 적용하는 계산법은 같을 수 있어. GPU가 활용할 수 있는 병렬성이 여기 있었던 거야. 

## 2. 그런데 물과 벽돌을 똑같은 공식으로 그릴 수는 없잖아?

초기의 그래픽 하드웨어는 정해진 기능을 빠르게 수행하는 성격이 강했어. 이후에는 그래픽 파이프라인의 일부를 **프로그래머가 작성한 코드로 바꿀 수 있게** 됐지. 이것이 프로그래머블 셰이더로 이어져. 

**셰이더(shader)는 그래픽 처리 과정의 특정 단계에서 실행되는 프로그램**이야. 물리적인 연산기 이름이 아니라, 그 연산기에서 실행할 코드인 거지.

예를 들어 정점 셰이더는 물체의 꼭짓점을 어디로 옮길지 계산하고, 프래그먼트 셰이더는 표면의 각 조각이 어떤 색으로 보일지 계산해. 여기서는 후자에 집중하자. 엄밀히는 최종 픽셀 자체가 아니라, 삼각형을 화면에 펼치는 과정에서 만들어진 **프래그먼트(fragment)** 를 처리하지만, 우선 “화면의 각 위치에서 표면색을 계산한다”고 생각하면 돼. 

가령 어떤 표면을 그리는 셰이더가 이런 계산을 한다고 해보자.

```text
그 위치의 표면색을 읽는다
→ 표면이 빛을 얼마나 정면으로 받는지 계산한다
→ 둘을 곱해서 출력할 색을 정한다
```

같은 표면을 그리는 동안에는 이 **하나의 프로그램**이 수많은 프래그먼트에 적용돼. 위치마다 입력이 다르므로 결과색은 달라지지만, 계산법은 같은 거야. 

프로그래머가 작성하는 것은 “이 지점의 색을 어떻게 계산할 것인가”라는 코드이고, GPU는 그 코드를 많은 지점에 적용해.

그런데 여기서, 그래픽과 별 상관없는 일을 하던 사람이 이 구조를 보게 된 거야.

## 3. “잠깐. 저 숫자가 꼭 색깔이어야 하나?”

GPU는 셰이더가 읽은 숫자를 사람이 “물의 색”이라고 부르는지, “온도”라고 부르는지 신경 쓰지 않아. 숫자를 읽어서 계산하고, 결과를 저장할 뿐이지.

그렇다면 입력에 색깔 대신 과학 계산용 데이터를 넣고, 셰이더에 조명 공식 대신 원하는 수식을 넣으면 어떨까? 실제로 당시 GPU는 이런 관점에서 **대량의 부동소수점 연산과 메모리 대역폭을 제공하는 계산 장치**로도 해석할 수 있었어. 

원래 하던 일을 써보면:

```text
각 픽셀에 대해:
    결과색 = 셰이더(그 위치의 입력)
```

여기서 이름만 조금 바꾸면:

```text
각 데이터 포인트에 대해:
    결과값 = 함수(그 데이터의 입력)
```

**“픽셀마다 같은 계산 파이프라인을 태운다”가  
“데이터 포인트마다 같은 계산 파이프라인을 태운다”로 바뀌는 순간이야.**

GPU를 새로 발명한 게 아니야. **기존 기계가 하던 일에서 ‘그림’이라는 의미를 벗겨낸 것**이지.

이런 방식으로 많은 데이터를 병렬 처리할 수 있는 계산이라면, 꼭 그래픽일 필요가 없었어. 이것이 초기 **GPGPU, General-Purpose Computing on GPUs**의 핵심 관점이야. 

다만 발견과 사용 사이에는 아주 우스운 장애물이 있었어.

## 4. “배열을 더하고 싶다고요? 우선 삼각형 두 개를 그리세요.”

우리가 하고 싶은 것은 단순해.

```text
C[i] = A[i] + B[i]
```

하지만 당시 GPU에 일을 시키는 통로는 그래픽 API였어. 그래서 초기 GPGPU에서는 계산을 그래픽 작업으로 바꿔서 제출했지. 배열을 **텍스처**, 즉 원래 표면의 무늬 같은 데이터를 담던 저장 구조에 넣고, 계산 결과는 이미지 출력 버퍼에 저장하는 식이었어. 

512×512개의 원소를 계산하고 싶다고 해보자.

먼저 출력 이미지 크기를 512×512로 설정해. 그리고 그 영역을 정확히 덮는 **삼각형 두 개**를 그려. 그러면 GPU가 그 영역의 각 위치에 대해 프래그먼트 셰이더를 실행하겠지.

이때 셰이더는 예쁜 색을 계산하는 대신, 입력 배열의 값을 읽고 원하는 계산을 해서 출력해. 결과로 나온 “이미지”를 숫자 배열로 해석하면 계산이 끝난 거야. 네가 가져온 강의에도 바로 이 우회 방식이 등장해. 

**GPU에게는 사각형을 그리는 작업인데, 연구자에게는 배열 전체에 함수를 적용하는 작업이었던 거야.**

이 우스운 상황을 NVIDIA의 2006년 발표 자료도 정확히 짚어. 텍스처를 읽고, 그래픽 파이프라인을 거쳐, 결과를 색으로 저장하는 과정을 보여준 다음 이렇게 적었어.

> “All this just to do A + B”

고작 A+B를 하려고 이 모든 과정을 거친다는 거지. 

게다가 단순히 코드가 번거로운 것만도 아니었어. 당시 프래그먼트 프로그램은 결과를 쓸 위치가 제한됐고, 다른 실행과 데이터를 주고받는 데에도 제약이 있었어.

**계산은 할 수 있는데, 입구부터 내부 규칙까지 여전히 그림을 그리는 기계에 맞춰져 있었던 거야.** 

## 5. NVIDIA는 “계산할 사람에게 그림을 그리라고 하지 말자”는 쪽으로 갔어

연구자들이 이미 GPU를 계산기로 쓰고 있다면, 그 우회를 정식 기능으로 만들 수 있겠지.

NVIDIA는 GPU의 병렬 처리 능력을 과학·연구용 계산에 직접 제공하는 방향으로 나아갔어. 2006년에 CUDA 아키텍처를 공개했고, 2007년에는 CUDA Toolkit 1.0이 나왔어. 

핵심 변화는 **삼각형을 그리지 않고도 GPU의 프로그래밍 가능한 연산부에 일을 맡길 수 있게 된 것**이야.

GPU 메모리를 일반적인 데이터 버퍼로 다루고, 더 일반적인 읽기·쓰기를 수행하며, 실행들 사이에서 데이터를 공유할 수 있는 기능도 제공했어. 단순히 셰이더의 이름을 바꾼 것 이상이었지. 

사용자가 하고 싶은 말은 이제 이것이었어.

**“그림을 그려줘”가 아니라, “이 프로그램을 많이 실행해줘.”**

여기서부터는 그 요청을 받아주는 **GPU 내부의 실행 엔진**을 들여다보자. 그림이라는 외피를 벗겨도, “같은 계산을 많은 데이터에 적용한다”는 성격은 그대로 남아 있어.

이제 개발 연대기에서 잠시 벗어나, 이 계산기를 설계하는 입장에서 생각해보는 거야.

## 6. 그래서 먼저 등장하는 개념이 warp야

32개의 데이터에 대해 덧셈을 해야 한다고 해보자.

각 계산은 서로 다른 값을 사용하지만, 지금 실행할 명령은 모두 덧셈이야. 그렇다면 실행마다 명령을 따로 지시하기보다는, **하나의 덧셈 명령으로 여러 데이터의 계산을 함께 진행**하는 편이 효율적이겠지.

NVIDIA는 프로그램의 개별 실행을 **thread**, 그 실행 32개를 묶어 관리하는 단위를 **warp**라고 해. 프로그래머에게는 각 thread의 동작을 쓰게 하면서, 하드웨어는 묶음 단위의 실행을 활용하는 방식이 **SIMT, Single Instruction, Multiple Threads**야. 

예를 들어 warp 하나가 덧셈 명령을 실행할 때는 이런 모습으로 생각할 수 있어.

```text
공통 명령: ADD

Thread 0   → a[0]  + b[0]
Thread 1   → a[1]  + b[1]
...
Thread 31  → a[31] + b[31]
```

중요한 것은 **warp가 연산기 32개로 이루어진 물리적 부품은 아니라는 점**이야. Warp는 실행을 묶어 관리하는 단위이고, 실제로 그것을 처리하는 회로는 별도로 있어.

32개의 thread가 특정 연산기 32개를 영구적으로 하나씩 차지한다는 뜻도 아니야. 

물론 같은 프로그램을 실행한다고 항상 같은 경로를 지나지는 않아. 어떤 thread는 `if`의 안쪽으로 가고, 다른 thread는 바깥쪽으로 갈 수 있지.

그러면 해당 명령을 실행하지 않는 thread를 비활성화하면서 각 경로를 처리해야 해. 이것이 **warp divergence**이고, 같은 warp 안에서 실행 경로가 비슷할수록 자원을 효율적으로 쓸 수 있는 이유야. 

여기까지 보면 좋은 방법을 찾은 것 같아.

같은 일을 하는 실행들을 묶어서 처리하면 된다는 거잖아.

그렇다면 다음 질문은 자연스럽게 이렇게 돼.

## 7. “그럼 GPU 안에 warp를 잔뜩 깔면 되는 거 아냐?”

우리는 방금 좋은 방법을 찾았어. 각 실행을 완전히 따로 지휘하는 대신, **32개의 thread를 warp로 묶어서 같은 명령을 함께 처리**하는 거야. 

그러면 이제 GPU를 크게 만드는 것도 간단해 보이지.

> “이런 계산을 처리할 연산기를 칩 안에 잔뜩 넣으면 되겠네?”

그런데 여기서 잠깐. **Warp는 처리할 실행의 묶음이지, 칩 위에 복사해서 붙일 수 있는 연산기 부품이 아니야.** 실제로 그 실행을 처리할 하드웨어는 아직 따로 생각해야 해.

그 하드웨어를 만드는 입장에서 생각해보자.

우리 프로그램은 덧셈 한 번으로 끝나지 않을 수 있어.

```text
입력을 읽는다
→ 곱한다
→ 그 결과를 더한다
→ 조건을 검사한다
→ 앞에서 계산한 값으로 다음 계산을 한다
```

그러려면 연산기뿐 아니라 **중간값을 보관할 자리**, **각 실행이 어디까지 진행됐는지 기억할 자리**, **다음에 어느 실행의 명령을 처리할지 고르는 장치**가 필요해. 실제 GPU에서는 레지스터와 실행 상태, 스케줄러가 이런 역할을 맡아. 

이제 이런 설계를 끝까지 밀어붙여보자.

> “모든 warp를 한곳에서 관리하고, GPU 전체에서 비어 있는 연산기 아무 데나 보내자.”

그런데 어떤 계산의 중간값은 칩 왼쪽에 있고, 지금 비어 있는 연산기는 오른쪽에 있다면?

**명령만 보내서는 안 돼. 그 명령에 필요한 값도 보내야 해.**

다음 연산을 다시 왼쪽에서 수행한다면 결과를 다시 가져와야겠지. 값의 저장 위치를 그대로 두고 멀리서 접근하도록 만들 수도 있지만, 이번에는 그 접근을 지원할 연결망이 필요해.

즉, 이 설계에서는 연산기를 늘릴수록 **“계산을 어디서 할까?”뿐 아니라 “그 계산에 필요한 상태를 어떻게 그곳까지 가져갈까?”**도 해결해야 해.

처음에는 연산기만 많이 넣으면 될 줄 알았는데, 어느새 칩 전체의 데이터 운송과 교통정리까지 설계하고 있는 거야.

## 8. “그럼 계산하는 곳과, 계산에 필요한 것들을 가까이 묶자.” — SM

여기서 설계 방향을 바꿔보자.

GPU 전체를 하나의 거대한 공용 계산기로 만들려고 하지 말고, **자기 몫의 실행을 관리할 수 있는 작은 병렬 프로세서**를 만들면 어떨까?

그 안에 연산기를 넣고, 바로 곁에 중간값을 담는 레지스터를 둬. 그 실행들을 관리하는 스케줄러와 가까이서 쓸 메모리도 함께 두는 거야.

NVIDIA GPU에서 이런 역할을 하는 하드웨어 단위가 **SM, Streaming Multiprocessor**야. SM은 연산 유닛, 로컬 레지스터, 스케줄러, shared memory와 L1 캐시 등의 자원을 갖고 있어. 

```text
SM
├── Warp scheduler: 어느 warp의 명령을 실행할지 선택
├── 연산 유닛: 실제 산술 연산 수행
├── 레지스터: 실행 중 필요한 값 보관
├── Load/store 장치: 메모리 읽기·쓰기 처리
└── Shared memory / L1 캐시: 가까이서 사용할 데이터 저장
```

여기서 두 개념이 딱 갈라져.

**Warp는 일을 묶는 방법이고, SM은 그 일을 맡아서 실행하는 기계야.**

SM 하나가 warp 하나 전용인 것도 아니야. 여러 warp의 실행 상태를 보관하면서, 그중 실행 가능한 명령들을 골라 자기 연산 자원에 공급해.

따라서 **보관하고 있는 warp 수와, 한순간에 실제 명령을 처리하는 연산기의 수는 다를 수 있어.** 

또 SM 전체에 스케줄러가 반드시 하나만 있는 것도 아니야. 예를 들어 Volta의 SM은 여러 스케줄러가 각자 담당하는 warp와 연산 자원을 갖는 식으로 내부도 나뉘어 있어. 우리가 지금 보고 있는 것은 이런 세부 구조를 묶어서 본 실행 엔진이야. 

## 9. “이 실행 엔진을 여러 개 배치하자.” — GPU

이제 GPU를 더 크게 만드는 방법도 달라져.

> “하나의 실행 엔진을 끝없이 거대하게 만들기보다, 이 엔진을 여러 개 배치하자.”

```text
GPU의 연산부

┌────────────────┐  ┌────────────────┐
│      SM 0      │  │      SM 1      │
│                │  │                │
│ 실행 관리      │  │ 실행 관리      │
│ 레지스터       │  │ 레지스터       │
│ 연산 유닛      │  │ 연산 유닛      │
│ 가까운 메모리  │  │ 가까운 메모리  │
└────────────────┘  └────────────────┘

┌────────────────┐  ┌────────────────┐
│      SM 2      │  │      SM 3      │
│       …        │  │       …        │
└────────────────┘  └────────────────┘
```

이렇게 여러 SM이 자기 몫의 실행을 처리하고, 그 바깥에 공유 캐시와 메모리 시스템 등이 연결돼. 실제 GPU에는 더 많은 구성 요소와 중간 계층이 있지만, **범용 계산의 중심을 보면 여러 SM으로 이루어진 구조**야. 

여기까지 오면 두 번의 설계 선택이 이어져.

Warp에서는 **“같은 명령을 함께 처리해서 제어 비용을 나누자”**고 했어.

그렇다고 GPU 전체가 모든 상태와 자원을 한데 공유하도록 밀어붙이지는 않아. SM에서는 **“서로 자주 주고받는 실행 상태와 연산 자원을 가까이 묶자”**고 하는 거야.

**공유해서 효율을 얻되, 그 공유 범위를 적당히 나누어서 크게 확장하는 것.**

이것이 SM의 자리를 이해하는 한 가지 설계 관점이야.

이제 기계는 준비됐어. 남은 것은 이 기계에 작업을 어떻게 표현해서 맡기느냐야.

## 10. “좋아. 그런데 내가 SM마다 일을 직접 나눠줘야 해?” — CUDA

이제 사용자의 문제가 남았어.

> “GPU 안에 실행 엔진이 여러 개 있다는 건 알겠어.  
> 그럼 내가 SM 0에는 이 일을, SM 1에는 저 일을 지정해야 하나?”

CUDA는 보통 그렇게 사용하게 만들지 않아.

대신 **각 실행이 할 일과, 그 실행들을 어떻게 묶어서 얼마나 실행할지** 표현하게 해. GPU에서 실행할 프로그램과 실행 규모를 지정하는 거야. 

프로그래머가 작성하는 것은 “어느 물리적 연산기를 써라”라는 배치도가 아니라, **할 일의 구성**이야.

그리고 PyTorch를 쓰면 이 실행 설정마저 아래에 숨겨져 있어. 우리는 텐서에 대한 연산을 요청하고, PyTorch의 CUDA 구현이 GPU에서 실행할 커널을 사용해. 

이제 입장을 바꿔보자.

지금까지는 아래에서 위로 기계를 만들었어.

이번에는 우리가 쓴 코드에서 출발해서, 그 요청이 **이미 살펴본 SM과 warp까지 어떻게 내려가는지** 따라가보는 거야.

## 11. `C = A + B` 한 줄에서 시작한다

```python
import torch

A = torch.randn(1024, 1024, device="cuda")
B = torch.randn(1024, 1024, device="cuda")

C = A + B
```

GPU에 있는 두 행렬의 **같은 위치에 있는 원소끼리 더하는 것**이야. 행렬 전체를 하나의 숫자로 합치는 것이 아니라, 원소별 덧셈을 해서 같은 크기의 결과 행렬을 만드는 거지. 

```text
C[0, 0] = A[0, 0] + B[0, 0]
C[0, 1] = A[0, 1] + B[0, 1]
C[0, 2] = A[0, 2] + B[0, 2]
...
```

여기서 첫 질문을 던져.

> **“첫 번째 덧셈이 끝나야 두 번째 덧셈을 할 수 있나?”**

아니야. 각 결과를 계산하는 데 필요한 것은 그 위치의 입력 두 개뿐이야. 옆 원소의 계산 결과를 기다릴 이유가 없어.

그렇다면 백만 개가 넘는 덧셈을 순서대로 하기보다, **여러 실행에 나눠 맡기면 되겠지.**

처음에 GPU에서 발견했던 바로 그 구조야.

```text
많은 데이터가 있고
→ 각 데이터에 같은 계산을 적용하면 되고
→ 서로 다른 데이터의 계산은 병렬로 진행할 수 있다
```

## 12. GPU에 건네는 것은 “각 실행이 할 일”이다 — Kernel과 thread

CUDA에서는 GPU에서 실행할 함수를 **커널(kernel)** 로 작성하고, 그 함수를 실행하는 논리적인 인스턴스를 **thread**라고 불러. 

우리 덧셈 커널이 각 thread에 시키는 일은 이것뿐이야.

> “네가 맡은 원소 번호를 알아내.  
> A와 B에서 그 원소를 읽어.  
> 더해서 C의 같은 위치에 써.”

행렬의 원소들을 한 줄로 번호 매겼다고 생각하면:

```text
Thread 0 → C[0] = A[0] + B[0]
Thread 1 → C[1] = A[1] + B[1]
Thread 2 → C[2] = A[2] + B[2]
...
```

**서로 다른 프로그램 백만 개를 만드는 게 아니야. 같은 프로그램을 실행하면서, 각자 다른 번호의 데이터를 처리하는 거야.** 

우리가 앞에서 warp를 설명할 때 말했던 “개별 실행”이, 프로그램을 작성하는 관점에서는 바로 이 thread야.

PyTorch는 이런 원소별 연산을 위한 CUDA 커널 구현을 제공해. 다만 아래에서는 **thread 하나가 원소 하나를 처리하는 교육용 구현**을 따라가자.

실제 PyTorch 커널은 한 thread가 여러 원소를 처리하는 등의 최적화를 사용할 수 있으므로, 아래 실행 설정이 실제 `A + B`의 내부 설정과 같다는 뜻은 아니야. 

중요한 것은 구체적인 튜닝값이 아니라, **행렬에 대한 요청이 어떤 실행 구조로 표현되는지**야.

## 13. “그 프로그램을 몇 개나 실행할 건데?” — Grid와 block

우리 예제에는 `1024 × 1024 = 1,048,576`개의 출력 원소가 있어.

Thread 하나에 원소 하나를 맡긴다면, 논리적 thread도 그만큼 필요해. CUDA에서는 이 thread들을 **block으로 묶고**, 이번 커널 실행의 모든 block을 **grid**라고 불러. 

설명용으로 block 하나에 256개 thread를 넣자.

```text
Grid: 이번 덧셈에 참여하는 전체 작업

├── Block 0: Thread 256개 → 원소   0~255
├── Block 1: Thread 256개 → 원소 256~511
├── Block 2: Thread 256개 → 원소 512~767
└── ...
```

그러면 필요한 block은 4,096개야. 실행 요청은 이런 모양이 돼.

```cpp
add<<<4096, 256>>>(device_a, device_b, device_c, 1024 * 1024);
```

말로 풀면:

> “`add` 커널을 실행해.  
> Block은 4,096개이고, 각 block에는 thread가 256개야.”

이렇게 커널과 실행 규모를 지정해서 제출하는 것이 **kernel launch**야. 

그런데 모든 thread가 같은 코드를 실행한다면, 자기 원소 번호는 어떻게 알아낼까?

```cpp
__global__ void add(
    const float* a,
    const float* b,
    float* c,
    int element_count
) {
    int index = blockIdx.x * blockDim.x + threadIdx.x;

    if (index < element_count) {
        c[index] = a[index] + b[index];
    }
}
```

`blockIdx`는 내 block의 번호, `blockDim`은 block 크기, `threadIdx`는 block 안에서 내 번호야. 이것들을 조합해 담당 원소를 정하는 거지. 

예를 들어 block 번호가 3이고, 그 안에서 내 thread 번호가 10이라면:

```text
index = 3 × 256 + 10
      = 778
```

이 thread는 `A[778]`과 `B[778]`을 더해서 `C[778]`에 저장해.

`if`는 담당 원소 번호가 실제 배열 범위를 벗어나는 경우를 막아줘. 이번 예제는 원소 수가 256으로 딱 나누어떨어지지만, 일반적인 크기에서는 마지막 block에 처리할 원소가 없는 thread가 생길 수 있거든. 

여기서 `256`은 하드웨어에 고정된 block 크기가 아니야. 커널을 사용하는 쪽에서 정한 값이야. 다만 block 크기에는 장치의 상한과 커널의 자원 사용량에 따른 제약이 있어. NVIDIA GPU의 대표적인 상한인 **1024 threads/block**도 이런 사양상의 제한이지, GPU 전체에서 실행할 수 있는 thread 수가 1024개라는 뜻은 아니야. 

또 block은 단순히 번호를 붙이기 위한 묶음만은 아니야. 같은 block의 thread들은 shared memory를 공유하고 `__syncthreads()`로 동기화할 수 있어. 다만 **이번 덧셈은 서로의 중간 결과가 필요 없으므로 그런 협력 기능을 사용하지 않을 뿐**이야. 

**여기까지 정한 것은 “할 일의 구성”이야. 아직 어떤 하드웨어가 누구의 일을 맡을지는 정하지 않았어.**

## 14. “백만 개의 thread를 실행하려면 코어도 백만 개가 필요한가?” — SM에 배치하기

아니야. **논리적인 실행 수와 물리적인 연산기 수는 달라.**

여기서 앞에서 만들었던 SM이 다시 등장해.

SM은 연산 유닛뿐 아니라 레지스터, 스케줄러, shared memory 등의 자원을 갖춘 실제 실행 엔진이었지. GPU는 grid의 block들을 이 SM들에 배치해. 

예를 들면 이런 배치가 가능해.

```text
제출한 작업                    실제 실행 엔진

Block 0 ───────────────────→ SM 2
Block 1 ───────────────────→ SM 0
Block 2 ───────────────────→ SM 3
Block 3 ───────────────────→ SM 2
...
```

**Block 하나는 같은 SM에서 실행되고, SM 하나에는 자원이 허용하는 만큼 여러 block이 함께 올라갈 수 있어.**

모든 block이 한꺼번에 올라가는 것은 아니야. 자리가 나면 남은 block들이 배치되고, 구체적인 배치 순서는 보장되지 않아. 

예를 들어 어떤 SM에 block 몇 개를 올렸더니, 그 SM이 보관할 수 있는 실행 상태나 레지스터 등의 자원이 찼다고 하자.

그러면 다른 block들은 다른 SM에 배치되거나 기다려야 해. 먼저 실행하던 block이 끝나서 자원이 확보되면, 그 자리에 다음 block을 배치할 수 있어. 

그러니까 GPU에 백만 개의 작업을 맡긴다는 것은, 백만 개의 물리적 코어를 요구하는 게 아니야.

**실행할 작업을 충분히 제출해두고, 실제 하드웨어가 나눠 처리하게 하는 거야.**

그리고 여기서 grid와 GPU의 차이도 분명해져.

**Grid는 이번 실행에 제출한 작업 전체이고, GPU는 그 작업을 받아 처리하는 기계야.**

Block이 4,096개라고 SM도 4,096개여야 하는 것이 아니고, grid 하나가 물리적인 GPU 부품 하나에 대응하는 것도 아니야. 

## 15. “그럼 SM은 thread를 하나씩 실행하나?” — Warp까지 내려가기

SM 하나에 배치된 block을 확대해보자.

우리 block에는 256개 thread가 있어. NVIDIA GPU는 같은 block 안의 thread를 연속된 번호 순서로 **32개씩 묶어 warp로 관리**해. 따라서 이 block에는 warp가 8개 생겨. 

```text
Block 0: 256 threads

Warp 0 → Thread   0~31
Warp 1 → Thread  32~63
Warp 2 → Thread  64~95
Warp 3 → Thread  96~127
Warp 4 → Thread 128~159
Warp 5 → Thread 160~191
Warp 6 → Thread 192~223
Warp 7 → Thread 224~255
```

이제 warp 0을 보자. 이 thread들이 해야 하는 일은 모두 같아.

```text
자기 A 값을 읽는다
→ 자기 B 값을 읽는다
→ 더한다
→ 자기 C 위치에 저장한다
```

덧셈 명령을 처리할 때는 이런 모습으로 생각하면 돼.

```text
Warp에 발행한 공통 명령: ADD

Thread 0  → A[0]  + B[0]
Thread 1  → A[1]  + B[1]
...
Thread 31 → A[31] + B[31]
```

**명령은 함께 처리하되, 각 thread의 데이터는 다른 것.**

앞에서 소개한 SIMT가, 지금 우리의 행렬 덧셈에서 실제로 나타나고 있는 거야. 

SM의 warp scheduler는 준비된 warp의 **다음 명령**을 골라 발행해. Warp 하나의 프로그램 전체를 끝내고 다음 warp로 넘어가야 하는 것은 아니야. 여러 warp의 명령 실행을 진행시키면서 연산 자원을 사용해. 

실행을 개념적으로 펼쳐보면 이런 모습이야. 아래는 실제 어셈블리나 정확한 사이클표가 아니라, 어떤 종류의 일이 진행되는지 보여주는 예시야.

```text
Warp 0: A의 담당 원소들을 읽는 명령
Warp 1: A의 담당 원소들을 읽는 명령
Warp 0: B의 담당 원소들을 읽는 명령
Warp 2: A의 담당 원소들을 읽는 명령
...
Warp 0: 준비된 값들을 더하는 명령
...
Warp 0: 결과를 C에 저장하는 명령
```

메모리 읽기·쓰기 명령은 그에 맞는 실행 경로를 사용하고, 덧셈 명령은 산술 연산 유닛을 사용해. **Warp가 특정 연산기를 계속 소유하는 것이 아니라, 명령을 실행할 때 필요한 SM의 자원을 사용하는 것**이야. 

또 32개 thread의 명령을 처리한다고 해서 반드시 물리적인 연산기 32개가 한 클록에 모두 처리한다는 뜻은 아니야. 예를 들어 Volta는 warp의 산술 명령을 여러 사이클에 걸쳐 처리하는 실행 구성을 갖고 있어. **Warp의 폭과 실제 연산기의 수, 명령 처리 시간은 구분해야 해.** 

여기서 `A + B` 한 줄이 드디어 실제 하드웨어 동작까지 내려온 거야.

> **전체로 보면 행렬 덧셈이고,  
> thread 하나가 보면 자기 원소의 덧셈이고,  
> SM이 보면 warp에 발행하는 읽기·덧셈·쓰기 명령들이야.**

## 16. 이제 “thread 하나만 실행하면?”이라는 질문에도 답할 수 있어

지금까지는 GPU에 일을 많이 줬어.

반대로, 다른 GPU 작업이 없는 상태에서 thread 하나만 실행한다고 생각해보자.

```cpp
add<<<1, 1>>>(device_a, device_b, device_c, 1);
```

Block이 하나이고, 그 안에 thread도 하나야.

하지만 실행을 관리할 때는 warp가 생기고, 그 warp에서 실제 작업을 가진 thread는 하나뿐이야. 나머지 lane은 사용되지 않아. 

```text
Block 0
└── Warp 0
    ├── Lane 0: 유효한 thread
    ├── Lane 1: 없음
    ├── Lane 2: 없음
    └── ...
```

이 block은 하나의 SM에 배치돼.

따라서 “CUDA core 하나를 영구적으로 점유한다”보다는, **“하나의 SM에서 실행되는 warp에 유효한 thread가 하나뿐이다”**가 정확한 설명이야.

그렇다면 block 하나를 최대 크기로 키우면 GPU 전체를 쓰게 될까?

```cpp
add<<<1, 1024>>>(device_a, device_b, device_c, 1024);
```

이 설정이 허용되는 장치와 커널이라면 총 1024개의 thread, 즉 32개의 warp가 생겨. 하지만 block은 여전히 하나이므로, 그 block은 하나의 SM에서 실행돼. **Thread가 많아졌다고 block 하나가 여러 SM으로 쪼개지는 것은 아니야.** 

반면 우리가 사용한 설정은:

```cpp
add<<<4096, 256>>>(device_a, device_b, device_c, 1024 * 1024);
```

여러 SM에 나눠 맡길 block이 충분히 있어.

이 차이를 보면, 왜 **“thread 수가 많다”와 “GPU 전체에 일이 잘 분산된다”가 같은 말은 아닌지** 알 수 있어.

GPU를 활용하려면 warp 안에 처리할 thread가 있어야 할 뿐 아니라, 여러 SM에 배치할 block도 있어야 하는 거야. 

## 17. 각자의 결과를 써놓으면, 행렬 덧셈이 끝난다

우리 덧셈 커널에서는 각 thread가 자기 원소를 계산해서 GPU 메모리의 `C`에 써.

```text
Thread 0 → C[0]에 저장
Thread 1 → C[1]에 저장
Thread 2 → C[2]에 저장
...
```

서로 다른 thread가 서로 다른 출력 위치를 담당하니까, CPU가 각 SM의 결과 조각을 받아서 다시 행렬로 조립할 필요는 없어. 모든 작업이 끝나면 결과는 이미 `C`의 각 위치에 들어 있어.

다만 여기서 “끝났다”는 말에는 두 시점이 있다는 것을 구분해야 해.

```python
C = A + B
```

이 호출이 반환되는 시점과 GPU가 실제 덧셈을 모두 끝낸 시점은 같지 않을 수 있어. PyTorch의 GPU 연산은 기본적으로 **비동기적으로 제출**되기 때문이야. CPU는 작업을 제출한 뒤 다음 일을 진행할 수 있어. 

같은 CUDA stream에 다음 GPU 작업을 제출하면, 그 작업은 앞선 작업 뒤에 실행되도록 순서가 유지돼. 따라서 그다음 연산이 `C`를 사용한다고 해서, 매번 CPU가 직접 계산 완료를 기다려야 하는 것은 아니야. 

반면 CPU에서 결과를 읽어야 하거나, GPU 계산 시간을 정확히 재려고 하는 등의 상황에서는 필요한 동기화가 있어야 해. **“실행 요청을 제출했다”와 “계산이 완료됐다”는 다른 사건**인 거지. 

---

이제 처음부터 끝까지 하나의 요청으로 연결해보자.

```text
PyTorch
“C = A + B를 계산해줘.”
        ↓
CUDA 커널 구현
“각 thread가 자기 원소 두 개를 읽고 더해서 저장하게 하자.”
        ↓
Kernel launch
“이 커널을 4,096개 block,
 block마다 256개 thread로 실행해.”
        ↓
GPU의 작업 배치
“이 block은 이 SM이 맡아.”
        ↓
SM의 warp scheduler
“이 warp의 다음 명령을 실행해.”
        ↓
SM 내부의 연산·메모리 유닛
실제 값을 읽고, 더하고, 결과를 쓴다.
        ↓
GPU 메모리의 C에 결과가 완성된다.
```

여기서 **grid와 block은 제출한 작업의 구조**, **thread는 프로그램의 논리적인 실행**, **warp는 그 실행들을 묶어 명령을 처리하는 단위**, **SM은 그 일을 실제로 수행하는 하드웨어**야. 

그리고 이 이야기는 처음의 삼각형 두 개로 돌아가.

예전에는 이렇게 말해야 했어.

> “이 사각형을 그려줘.  
> 그런데 각 위치의 색은 A와 B의 값을 더해서 정해줘.”

이제는 이렇게 말하면 돼.

```python
C = A + B
```

**계속 같았던 것은 ‘많은 데이터에 같은 계산을 적용한다’는 일이야. 달라진 것은, 그 일을 시키기 위해 더 이상 그림을 그리는 척할 필요가 없어졌다는 거지.**
