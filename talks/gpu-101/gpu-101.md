## 1. 시작은 “게임 화면을 제시간에 그려라”였어

게임 속에서 햇빛이 비치는 호숫가를 걷고 있다고 해보자. 카메라가 움직일 때마다 물결의 모양도, 나무가 가리는 부분도, 수면에 비치는 빛도 달라져야 해.

컴퓨터가 가진 것은 나무와 수면을 나타내는 **삼각형들, 재질, 조명, 카메라 위치**야. 이것을 가지고 화면의 각 위치에 어떤 색을 표시할지 계산해야 해. 이 작업이 **렌더링**이고, GPU는 원래 이런 3D 그래픽을 빠르게 처리하기 위해 발전한 장치야. 

그런데 화면에는 픽셀이 엄청나게 많아. 가령 약 200만 픽셀짜리 화면을 초당 60장씩 만들어야 한다면, 매초 1억 개가 넘는 출력 픽셀의 색을 만들어야 하지.

여기서 눈여겨볼 점은 단순히 “계산이 많다”가 아니야.

**서로 다른 위치에 대해, 비슷한 계산을 엄청나게 많이 한다는 것**이야.

수면의 이 지점에서도 빛의 반사를 계산하고, 바로 옆 지점에서도 빛의 반사를 계산해. 들어가는 위치와 방향은 다르지만, 적용하는 계산법은 같을 수 있어. GPU가 활용할 수 있는 병렬성이 여기 있었던 거야. 

## 2. 그런데 물과 벽돌을 똑같은 공식으로 그릴 수는 없잖아?

초기 OpenGL의 **고정 기능 경로**에서는 조명의 색, 재질의 반짝임, 텍스처 같은 설정을 넘기면 준비된 연산을 그래픽 하드웨어가 수행했어. 같은 계산을 많은 위치에서 빠르게 반복하기에는 좋았지만, 더 다양한 재질을 표현하려면 반복할 계산 자체도 바꾸고 싶어졌지.

처음의 수면을 생각해보자. 시간에 따라 물결의 방향을 바꾸고, 물결 때문에 반사된 풍경이 흔들리게 하고, 보는 각도에 따라 반사 비율도 달라지게 하고 싶어. 이런 계산을 미리 준비된 설정의 조합으로 표현하는 데는 한계가 있었어. 여러 번 그리거나 확장 기능을 사용해 표현하는 방법도 있었지만, 개발자가 계산 순서를 직접 작성할 수 있으면 훨씬 자유로워지겠지.

슬라이드에서는 같은 큐브·바닥·반투명 판 장면을 네 단계로 따라가. 정점을 카메라 기준으로 변환한 모습 → 삼각형이 덮는 샘플에 생성된 프래그먼트 → 텍스처와 조명으로 계산한 후보 색 → 깊이 검사와 투명도 혼합을 마친 최종 픽셀이야. 앞의 세 그림은 자체 소프트웨어 렌더러의 중간 데이터를 보여주는 진단 화면이고, 실제 GPU 내부를 촬영한 것은 아니야. 특히 색 계산 화면은 깊이 검사와 혼합을 꺼서, 뒤늦게 그린 물체가 앞의 물체를 덮는 문제를 보여줘. 다음 장에서는 이 네 단계의 위치를 유지한 채 고정 기능과 프로그래머블 하드웨어를 비교해.

그래서 그래픽 API와 하드웨어가 함께 발전하면서, 파이프라인의 일부를 **프로그래머가 작성한 코드로 바꿀 수 있게** 됐어. 프로그래머블 셰이더는 이렇게 필요한 표면 계산을 직접 쓰려는 요구에서 이해할 수 있어.

실제로 바뀐 부분을 같은 위치에 놓고 비교해보자. GeForce 256 시대의 GPU는 정점 변환·조명과 텍스처 결합에 정해진 처리 회로를 사용했어. GeForce FX 시대에는 그 자리에 **명령을 받아 실행하는 정점 프로세서와 프래그먼트 프로세서**가 있어. 각 프로세서에는 값을 보관할 레지스터와 실제 계산을 하는 연산기가 필요해.

```text
GeForce 256 시대
정점 → 고정 변환·조명 → rasterizer → 고정 텍스처 결합 → depth/blend → 출력

GeForce FX 시대
         정점 프로그램                  프래그먼트 프로그램
               ↓                                ↓
정점 → 정점 프로세서 → rasterizer → 프래그먼트 프로세서 → depth/blend → 출력
        레지스터·연산기                   레지스터·연산기
```

rasterizer는 삼각형을 화면의 조각들로 바꾸고, depth/blend는 가려짐과 색의 합성을 처리해. 이런 전용 단계까지 전부 프로그램으로 바뀐 것은 아니야. OpenGL은 이 기능을 쓰는 API이고, 그림은 그 파이프라인을 구현한 대표적인 하드웨어의 변화를 보여줘.

**셰이더(shader)는 그래픽 처리 과정의 특정 단계에서 실행되는 프로그램**이야. 물리적인 연산기 이름이 아니라, 그 연산기에서 실행할 코드인 거지.

예를 들어 정점 셰이더는 물체의 꼭짓점을 어디로 옮길지 계산하고, 프래그먼트 셰이더는 표면의 각 조각이 어떤 색으로 보일지 계산해. 여기서는 후자에 집중하자. 엄밀히는 최종 픽셀 자체가 아니라, 삼각형을 화면에 펼치는 과정에서 만들어진 **프래그먼트(fragment)** 를 처리하지만, 우선 “화면의 각 위치에서 표면색을 계산한다”고 생각하면 돼. 

가령 수면을 그리는 셰이더가 이런 계산을 한다고 해보자.

```text
위치와 시간에 맞는 물결의 표면 방향을 구한다
→ 그 방향으로 반사되는 풍경을 읽는다
→ 보는 각도에 따라 물의 색과 반사색을 섞는다
```

물결의 표면 방향은 normal이라고 하는 벡터로 나타낼 수 있어. 시간에 따라 움직이는 normal 데이터를 읽거나 계산하고, 반사색을 구하는 데 사용하는 거지. 물결을 만드는 법과 색을 섞는 법은 개발자가 정해. 완전한 물리 시뮬레이션이 아니라, 직접 쓸 수 있는 계산의 예야.

이 코드가 실행될 때는 명령을 제어하는 회로가 다음 연산을 지시하고, 텍스처에서 읽은 값과 중간 결과는 레지스터에 놓여. 여러 물리 연산기가 그 값으로 계산하고 결과를 다음 그래픽 단계에 넘기지. **셰이더는 명령을 제공하는 코드이고, 프로세서는 그 명령과 데이터를 받아 계산하는 하드웨어**야. 프로그램이 GPU 안의 어느 회로에 도착하는지까지 연결해서 보아야 해.

같은 수면을 그리는 동안에는 이 **하나의 프로그램**이 수많은 프래그먼트에 적용돼. 위치마다 입력이 다르므로 결과색은 달라지지만, 계산법은 같은 거야.

프로그래머가 작성하는 것은 “이 지점의 색을 어떻게 계산할 것인가”라는 코드이고, GPU는 그 코드를 많은 지점에 적용해.

그런데 여기서, 그래픽과 별 상관없는 일을 하던 사람이 이 구조를 보게 된 거야.

## 3. “잠깐. 저 숫자가 꼭 색깔이어야 하나?”

GPU는 셰이더가 읽은 숫자를 사람이 “물의 색”이라고 부르는지, “온도”라고 부르는지 신경 쓰지 않아. 숫자를 읽어서 계산하고, 결과를 저장할 뿐이지.

그렇다면 입력에 색깔 대신 과학 계산용 데이터를 넣고, 셰이더에 조명 공식 대신 원하는 수식을 넣으면 어떨까? 실제로 당시 GPU는 이런 관점에서 **대량의 부동소수점 연산과 메모리 대역폭을 제공하는 계산 장치**로도 해석할 수 있었어. 

원래 하던 일을 써보면:

```text
각 픽셀에 대해:
    결과색 = 셰이더(그 위치의 입력)
```

여기서 이름만 조금 바꾸면:

```text
각 데이터 포인트에 대해:
    결과값 = 함수(그 데이터의 입력)
```

**“픽셀마다 같은 계산 파이프라인을 태운다”가  
“데이터 포인트마다 같은 계산 파이프라인을 태운다”로 바뀌는 순간이야.**

GPU를 새로 발명한 게 아니야. **기존 기계가 하던 일에서 ‘그림’이라는 의미를 벗겨낸 것**이지.

이런 방식으로 많은 데이터를 병렬 처리할 수 있는 계산이라면, 꼭 그래픽일 필요가 없었어. 이것이 초기 **GPGPU, General-Purpose Computing on GPUs**의 핵심 관점이야. 

다만 발견과 사용 사이에는 아주 우스운 장애물이 있었어.

## 4. “배열을 더하고 싶다고요? 우선 삼각형 두 개를 그리세요.”

우리가 하고 싶은 것은 단순해.

```text
C[i] = A[i] + B[i]
```

하지만 당시 GPU에 일을 시키는 통로는 그래픽 API였어. 그래서 초기 GPGPU에서는 계산을 그래픽 작업으로 바꿔서 제출했지. 배열을 **텍스처**, 즉 원래 표면의 무늬 같은 데이터를 담던 저장 구조에 넣고, 계산 결과는 이미지 출력 버퍼에 저장하는 식이었어. 

512×512개의 원소를 계산하고 싶다고 해보자.

먼저 출력 이미지 크기를 512×512로 설정해. 그리고 그 영역을 정확히 덮는 **삼각형 두 개**를 그려. 그러면 GPU가 그 영역의 각 위치에 대해 프래그먼트 셰이더를 실행하겠지.

이때 셰이더는 예쁜 색을 계산하는 대신, 입력 배열의 값을 읽고 원하는 계산을 해서 출력해. 결과로 나온 “이미지”를 숫자 배열로 해석하면 계산이 끝난 거야. 네가 가져온 강의에도 바로 이 우회 방식이 등장해. 

**GPU에게는 사각형을 그리는 작업인데, 연구자에게는 배열 전체에 함수를 적용하는 작업이었던 거야.**

이 우스운 상황을 NVIDIA의 2006년 발표 자료도 정확히 짚어. 텍스처를 읽고, 그래픽 파이프라인을 거쳐, 결과를 색으로 저장하는 과정을 보여준 다음 이렇게 적었어.

> “All this just to do A + B”

고작 A+B를 하려고 이 모든 과정을 거친다는 거지. 

게다가 단순히 코드가 번거로운 것만도 아니었어. 당시 프래그먼트 프로그램은 결과를 쓸 위치가 제한됐고, 다른 실행과 데이터를 주고받는 데에도 제약이 있었어.

**계산은 할 수 있는데, 입구부터 내부 규칙까지 여전히 그림을 그리는 기계에 맞춰져 있었던 거야.** 

## 5. NVIDIA는 “계산할 사람에게 그림을 그리라고 하지 말자”는 쪽으로 갔어

연구자들이 이미 GPU를 계산기로 쓰고 있다면, 그 우회를 정식 기능으로 만들 수 있겠지.

NVIDIA는 GPU의 병렬 처리 능력을 과학·연구용 계산에 직접 제공하는 방향으로 나아갔어. 2006년에 CUDA 아키텍처를 공개했고, 2007년에는 CUDA Toolkit 1.0이 나왔어. 

핵심 변화는 **삼각형을 그리지 않고도 GPU의 프로그래밍 가능한 연산부에 일을 맡길 수 있게 된 것**이야.

그런데 요청하는 말만 바꾼다고 이 일이 가능해지는 것은 아니야. 그 요청을 처리할 하드웨어도 필요해. GeForce 7의 그래픽 경로에는 정점 전용 프로세서 묶음과 픽셀 전용 프로세서 묶음이 따로 있었어. 정점 처리가 끝나면 rasterizer를 거쳐 픽셀 쪽으로 넘어가고, 결과는 그래픽 출력 경로로 메모리에 기록됐지.

2006년 **G80, 즉 GeForce 8800**에서는 같은 종류의 프로세서가 정점·픽셀·계산 작업에 쓰일 수 있게 했어. CUDA의 커널 실행 요청은 rasterizer를 거치지 않고 이 프로세서들로 전달돼. 프로세서는 여러 지역 그룹으로 조직되고, 각 그룹에는 작업값을 보관할 레지스터와 협력하는 실행들이 쓸 shared memory가 있어. 메모리의 배열 주소를 계산해 읽고 쓰는 경로도 연결되지.

```text
GeForce 7의 그래픽 경로        G80의 CUDA 계산 경로

정점 전용 프로세서들          CUDA kernel / launch
        ↓                            ↓
    rasterizer                 실행 요청 분배
        ↓                     ↙              ↘
픽셀 전용 프로세서들       프로세서 그룹    프로세서 그룹
   ↑            ↓         레지스터         레지스터
텍스처 읽기  depth/blend   같은 종류의 SP들 같은 종류의 SP들
   ↑            ↓         shared memory    shared memory
     장치 메모리              ↕              ↕
                         일반 읽기·쓰기 ↔ 장치 메모리
```

이 비교는 선택한 자원과 기능상의 연결만 보여줘. G80에도 그래픽 전용 경로는 남아 있어. 또 **프로세서의 역할을 통합했다는 것이 GPU 전체에 레지스터나 shared memory 하나만 두었다는 뜻은 아니야.** 가까운 자원을 가진 그룹이 반복되는 구조라는 점은 뒤의 SM 설명에서 다시 볼 거야.

앞의 프래그먼트 경로에서도 텍스처의 여러 위치를 읽을 수는 있었어. 하지만 일반 배열의 원하는 위치에 결과를 쓰고, 여러 실행이 중간값을 주고받으며 협력하려면 다른 지원이 필요했지. **계산을 표현하는 모델과 그것을 실행할 프로세서가 함께 발전한 것**이야.

그래서 CUDA 도입 전 GPU에 Toolkit만 설치한다고 CUDA 장치가 되지는 않아. 셰이더로 계산할 수 있다는 것과 CUDA의 실행·메모리 모델을 하드웨어가 지원한다는 것은 달라. 반대로 예전에 CUDA를 지원하던 GPU가 최신 Toolkit의 지원 대상에서 빠지는 것은 별도의 버전 지원 문제야. 그 경우에는 호환되는 이전 Toolkit과 드라이버를 사용하는 길이 있을 수 있어.

사용자가 하고 싶은 말은 이제 이것이었어.

**“그림을 그려줘”가 아니라, “이 프로그램을 많이 실행해줘.”**

여기서부터는 그 요청을 받아주는 **GPU 내부의 실행 엔진**을 들여다보자. 그림이라는 외피를 벗겨도, “같은 계산을 많은 데이터에 적용한다”는 성격은 그대로 남아 있어.

이제 개발 연대기에서 잠시 벗어나, 이 계산기를 설계하는 입장에서 생각해보는 거야.

## 6. 그래서 먼저 등장하는 개념이 warp야

여러 데이터에 대해 덧셈을 해야 한다고 해보자.

각 계산은 서로 다른 값을 사용하지만, 지금 실행할 명령은 모두 덧셈이야. 그렇다면 실행마다 명령을 따로 지시하기보다는, **하나의 덧셈 명령으로 여러 데이터의 계산을 함께 진행**하는 편이 효율적이겠지.

프로그램의 개별 실행을 **thread**라고 해. 여기서 살펴보는 NVIDIA CUDA GPU에서 **warp는 하드웨어가 실행을 묶어 관리하는 32개 논리적 thread의 묶음**이야. 같은 작업 묶음인 block 안에서 연속된 thread 번호 순서로 묶어. Block을 어떻게 구성하는지는 뒤의 코드 예제에서 볼 거야.

함께 처리하면 제어 비용을 나눌 수 있다는 것이 묶는 이유이고, NVIDIA CUDA GPU가 사용하는 묶음의 폭은 32인 거지. Warp 안에서 0번부터 31번까지의 논리적인 thread 자리를 **lane**이라고 불러.

프로그래머에게는 각 thread의 동작을 쓰게 하면서, 하드웨어는 묶음 단위의 실행을 활용하는 방식이 **SIMT, Single Instruction, Multiple Threads**야.

예를 들어 한 warp에 속한 thread들의 덧셈을 생각해보자.

```text
이 warp의 thread들에 공통으로 적용할 명령: ADD

Thread 0   → a[0]  + b[0]
Thread 1   → a[1]  + b[1]
...
Thread 31  → a[31] + b[31]
```

중요한 것은 **warp가 연산기 32개로 이루어진 물리적 부품은 아니라는 점**이야. Warp는 논리적 thread의 묶음이고, 그 thread들의 명령을 실제로 처리하는 회로는 별도로 있어.

32개의 thread가 특정 연산기 32개를 영구적으로 하나씩 차지한다는 뜻도 아니야. 이제 이 명령들을 처리할 하드웨어에 무엇이 필요한지 하나씩 준비해보자.

## 7. “이 실행들을 진행하려면 무엇이 필요할까?”

여기부터는 실제 GPU가 발명된 순서를 재현하는 이야기가 아니라, 계산기를 설계하는 사고실험이야.

프로그램은 덧셈 한 번으로 끝나지 않을 수 있어.

```text
입력을 읽는다
→ 곱한다
→ 그 결과를 더한다
→ 앞에서 계산한 값으로 다음 계산을 한다
→ 결과를 저장한다
```

먼저 읽어온 입력과 계산 중간값을 잠깐 보관해야 해. 각 thread가 이런 작업값을 두는 자리가 **레지스터**이고, 이 값들을 보관하고 읽고 쓰게 해주는 하드웨어 저장 자원이 **레지스터 파일(register file)**이야. 같은 warp에 속해 있어도 각 thread는 자기 값을 사용해.

값만 기억해서는 프로그램을 이어갈 수 없어. 각 실행이 어디까지 진행됐는지, 어떤 명령이 앞선 계산이나 메모리 읽기를 기다리는지도 알아야 해. 이런 **실행 상태(execution state)**를 보관하고 관리할 자리도 필요해. 레지스터의 계산값과 실행을 관리하는 정보를 함께 갖고 있어야 다음 일을 진행할 수 있는 거지.

여러 warp의 상태를 보관하고 있다면, 그중 어느 warp의 명령을 다음에 처리할지도 골라야 해. 이 선택과 발행을 맡는 자원이 **warp scheduler**야. 스케줄러가 필요한 값과 실행 자원이 준비된 명령을 골라 발행해. 한 warp에 속한 thread들의 프로그램 전체가 끝나기 전에도, 다른 warp의 준비된 명령을 발행할 수 있어.

발행된 명령을 실제로 처리할 장치도 있어야겠지. **산술 연산 유닛**은 레지스터에서 가져온 값으로 덧셈과 곱셈 같은 계산을 해. **Load/store 유닛**은 메모리에서 값을 읽거나 메모리에 결과를 쓰는 명령을 처리해. 스케줄러가 명령을 발행하고, 명령 종류에 맞는 유닛이 그 명령을 처리하는 거야.

이렇게 실행에 필요한 상태와 자원을 하드웨어에 배정받은 warp를 **resident warp**라고 해. 실행 자원을 배정받았더라도, 다음 명령은 필요한 값이 도착할 때까지 기다릴 수 있어.

여기까지는 값을 보관하고, 진행 상태를 관리하고, 준비된 명령을 골라 실제로 처리하는 역할을 정했어. **이제 각 자원을 몇 개 두고, 어떻게 연결할지 정해보자.** 이런 구성을 생각할 수 있겠지.

> “GPU 전체에 거대한 레지스터 파일 하나를 두고, 수많은 warp의 상태를 보관하자.
> 스케줄러 하나가 이 warp들의 준비 상태를 확인해 명령을 발행하면 되겠네.
> 산술 연산 유닛과 load/store 유닛도 많이 붙여 놓고, 빈 곳으로 명령을 보내면 되는 거 아니야?”

```text
GPU 전체를 하나의 실행 영역으로 만든다는 가정

수많은 resident warp의 실행 상태
                ↓ 준비 상태 참조
        중앙 warp scheduler 하나
                ↓ 명령 선택 · 발행
수많은 산술 연산 유닛 / load·store 유닛
                ↕ 피연산자와 결과
         거대한 레지스터 파일
```

그런데 레지스터 파일이 칩 왼쪽에 있고, 지금 쓸 수 있는 연산기는 오른쪽에 있다고 해보자.

**스케줄러가 ADD 명령을 발행하면, 그 명령에 참여하는 thread들의 피연산자도 연산 유닛에 전달해야 해.** 계산한 결과는 레지스터에 기록해 다음 명령에서 다시 사용할 수 있어야 하고.

연산기가 많아지면 여러 곳에서 레지스터의 값을 읽고 결과를 쓰려고 하겠지. 그 값을 공급할 저장 장치의 대역폭과 연결망도 함께 갖춰야 해. 값의 자리를 고정하고 멀리서 접근하든, 값을 연산기 근처로 옮기든 데이터가 오가는 비용을 생각해야 하는 거야.

제어도 비슷해. 중앙 스케줄러는 각 warp의 다음 명령이 준비됐는지, 어느 실행 유닛이 새 명령을 받을 수 있는지 알아야 해. 실행 결과에 따라 준비 상태를 갱신하고, 스케줄러가 발행한 명령을 칩 곳곳에 전달하는 연결도 필요하지.

이 설계에서 규모를 키우려면 연산기 수뿐 아니라 **레지스터 접근, 피연산자와 결과의 이동, 준비 상태와 명령의 전달**도 함께 감당해야 해. 그러면 자주 주고받는 범위를 좀 더 가까운 곳으로 좁혀 보면 어떨까?

## 8. “그럼 계산하는 곳과, 계산에 필요한 것들을 가까이 묶자.” — SM

한 무리의 warp를 맡을 실행 엔진을 만들어보자. 그 warp들의 실행 상태와 thread별 레지스터 값을 가까이 두고, 명령을 고를 스케줄러와 실제로 처리할 산술·load/store 유닛도 함께 배치하는 거야.

그러면 명령을 선택하고, 작업값을 읽고, 계산 결과를 다시 기록하는 자주 반복되는 일이 이 실행 엔진 가까이에서 일어나게 할 수 있어. 여러 warp가 사용할 자원을 한곳에 갖추되, 그 관리와 데이터 이동의 범위를 나누는 거지.

NVIDIA GPU에서 이런 역할을 하는 하드웨어 단위가 **SM, Streaming Multiprocessor**야. SM은 스케줄러, 실행 상태를 관리하는 자원, 레지스터 파일, 연산 유닛 등을 갖춰 자기 몫의 warp들을 실행해. 가까이서 데이터를 사용할 수 있도록 shared memory와 L1 캐시 같은 저장 자원도 있어.

```text
SM
├── 실행 상태: resident warp들의 진행과 준비 상태 관리
├── Warp schedulers: 준비된 warp의 명령을 선택해 발행
├── 레지스터 파일: resident thread들의 작업값 보관
├── 산술 연산 유닛: 실제 덧셈·곱셈 수행
├── Load/store 유닛: 메모리 읽기·쓰기 처리
└── Shared memory / L1 캐시: 가까이서 사용할 데이터 저장
```

**Warp는 일을 묶는 방법이고, SM은 그 일을 맡아서 실행하는 기계야.**

SM 하나는 여러 warp의 실행 상태를 보관하면서, 그중 준비된 명령들을 골라 자기 연산 자원에 공급해. 기다리는 warp의 상태를 보관해 둔 채 다른 warp의 명령을 처리할 수 있는 거지.

그래서 **이 SM에 머무는 warp 수와, 한순간에 명령을 처리하는 연산기 수는 서로 다른 숫자야.**

실제 내부는 공식 세부 도식이 공개된 **RTX Blackwell** SM으로 보자. 구획이 네 개 있고, 각 구획에는 warp 스케줄러 하나와 64 KB 레지스터 파일, FP32 또는 INT32 연산 유닛 32개, 5세대 Tensor Core 하나, load/store 유닛 네 개가 있어. FP32/INT32는 같은 유닛을 공유하므로 한 사이클에 둘 중 한 종류의 연산을 처리해. 스케줄러 네 개가 warp 네 개라는 뜻은 아니야.

Tensor Core는 지원하는 행렬 곱셈·누적에 특화된 실행 자원이야. 이런 자원을 추가한 이유는 GPU 전체를 구성한 다음에 살펴보자.

그림에서는 구획들을 네 열로 펼쳤어. 맨 아래 128 KB L1 데이터 캐시와 shared memory는 네 구획이 함께 쓰는 SM의 저장 자원이야. 명령 캐시, dispatch, 특수 함수 및 그래픽스 전용 자원은 생략했어. 실제 다이의 면적 비율이나 배선도는 아니야. 최신 공개 세대인 Rubin의 SM 내부 수치로 받아들이면 안 돼.

이렇게 자기 몫의 실행 상태와 자원을 갖춘 단위를 만들었어.

## 9. “이 실행 엔진을 여러 개 배치하자.” — GPU

이제 GPU를 더 크게 만드는 방법도 달라져.

> “하나의 실행 엔진을 끝없이 거대하게 만들기보다, 이 엔진을 여러 개 배치하자.”

```text
GPU의 연산부

┌────────────────┐  ┌────────────────┐
│      SM 0      │  │      SM 1      │
│                │  │                │
│ 실행 관리      │  │ 실행 관리      │
│ 레지스터       │  │ 레지스터       │
│ 연산 유닛      │  │ 연산 유닛      │
│ 가까운 메모리  │  │ 가까운 메모리  │
└────────────────┘  └────────────────┘

┌────────────────┐  ┌────────────────┐
│      SM 2      │  │      SM 3      │
│       …        │  │       …        │
└────────────────┘  └────────────────┘
```

이렇게 여러 SM이 자기 몫의 실행을 처리하고, 그 바깥에 공유 캐시와 메모리 시스템 등이 연결돼. 실제 GPU에는 더 많은 구성 요소와 중간 계층이 있지만, **범용 계산의 중심을 보면 여러 SM으로 이루어진 구조**야. 

여기까지 오면 두 번의 설계 선택이 이어져.

Warp에서는 **“같은 명령을 함께 처리해서 제어 비용을 나누자”**고 했어.

그렇다고 GPU 전체가 모든 상태와 자원을 한데 공유하도록 밀어붙이지는 않아. SM에서는 **“서로 자주 주고받는 실행 상태와 연산 자원을 가까이 묶자”**고 하는 거야.

**공유해서 효율을 얻되, 그 공유 범위를 적당히 나누어서 크게 확장하는 것.**

이것이 SM의 자리를 이해하는 한 가지 설계 관점이야.

이제 여러 SM으로 확장하는 원리는 생겼어. 실제 GPU는 무엇을 더 발전시켜야 할까? 그 답은 이 기계에 맡기는 일에서도 찾아야 해.

### 2012년 AlexNet: 그림을 그리던 GPU로 그림을 알아보는 법을 학습한다

여기서 기계에 맡기는 일이 달라진 사례를 보자. Krizhevsky, Sutskever, Hinton의 AlexNet은 2012년 ImageNet 대회에서 큰 성과를 냈어. 합성곱 신경망은 많은 이미지 위치에 필터 계산을 적용하고, 학습 과정에서 그 필터를 바꿔. 연구진은 이런 계산을 GPU에서 효율적으로 수행하도록 CUDA 코드를 구현했어. 논문에 따르면 **NVIDIA GTX 580 두 장으로 한 네트워크를 학습하는 데 약 5~6일**이 걸렸지.

장당 메모리는 3GB였어. 원하는 규모의 네트워크를 한 장에 담기 어려워 두 GPU에 나눴고, 일부 층에서만 데이터를 교환하도록 연결도 정했어. **하드웨어의 저장 용량과 통신 비용이 모델의 분할과 연결 구조에 영향을 준 것**이야. 메인 도식은 이 관계를 보여주는 개념도이며 SM 개수나 정확한 층별 배치를 재현하지 않아.

이것이 GPU 학습의 최초 사례이거나, AlexNet 하나 때문에 이후 모든 GPU 기능이 생겼다는 뜻은 아니야. 기존 CUDA 실행 자원을 잘 활용한 성과가 GPU 학습의 가능성을 보여줬고, 과학 계산과 딥러닝의 규모가 커지면서 하드웨어와 구현도 계속 발전했어. 이제 저장할 **용량**과는 별개의 문제, 계산할 데이터를 얼마나 빨리 공급하는가를 보자.

### 읽고 쓰는 프로그램은 같아도, 메모리를 연결하는 방식은 달라진다

과학 계산과 딥러닝에는 큰 데이터를 계속 읽고 쓰는 일이 많아. 연산기를 늘려도 데이터가 제때 도착하지 않으면 기다리게 되지. **대역폭은 단위 시간에 얼마나 많은 데이터를 옮길 수 있는지**를 나타내. 이를 높이기 위해 메모리의 물리적인 연결 방식도 바뀌었어.

이전 GDDR5 구성에서는 GPU 패키지 주변에 별도 메모리 패키지들을 놓고 보드 위의 배선으로 연결했어. GPU 안의 SM이 요청한 값은 캐시와 메모리 컨트롤러를 거쳐 이 메모리와 오가지. 2016년 P100은 여러 층으로 쌓은 HBM2와 GPU 다이를 **같은 패키지**에 놓았어. 아래의 silicon interposer가 메모리 스택과 GPU를 넓게 연결해 더 많은 데이터를 공급할 수 있게 해.

```text
          CUDA 커널: 입력을 읽는다 → 계산한다 → 결과를 쓴다
                   ↓                              ↓
 GDDR5 패키지 ↔ GPU 패키지 ↔ GDDR5 패키지     하나의 패키지 안
      보드 위의 별도 메모리들              HBM2 ↔ GPU 다이 ↔ HBM2
                                            silicon interposer
```

위의 커널은 두 경우 모두 일반적인 읽기와 쓰기를 해. HBM을 사용하려고 새로운 HBM 전용 CUDA 명령을 작성하는 것은 아니야. 프로그램은 데이터를 효율적으로 읽고 재사용하도록 구성하고, 하드웨어는 그 데이터를 공급할 물리적인 폭을 넓히는 거지. HBM은 오늘날 언어 모델보다 먼저 HPC와 딥러닝에 사용됐어.

### 행렬 커널의 명령 경로와 실제 계산 회로가 함께 달라진다

신경망에는 큰 행렬의 곱셈과 누적이 반복돼. Pascal도 필요한 값을 읽고 곱셈·덧셈 명령을 반복해서 이 계산을 할 수 있었어. 레지스터가 값을 공급하면 일반 산술 유닛이 그 명령을 처리하는 경로였지.

2017년 Volta에는 작은 행렬 타일을 곱하고 누적하는 **Tensor Core**와 데이터 경로가 추가됐어. 일반 산술 유닛은 그대로 두면서 행렬 연산에 특화된 회로를 더한 거야. CUDA 9의 cuBLAS·cuDNN 구현과 WMMA라는 행렬 연산 인터페이스는 그 자원을 사용하는 명령 경로를 제공했어.

```text
Pascal의 일반 산술 경로          Volta + CUDA 9의 행렬 경로
행렬 곱셈 커널                   대응 라이브러리 / WMMA 커널
        ↓                                  ↓
곱셈·누적 명령을 반복             지원하는 행렬 곱셈·누적 명령
        ↓                                  ↓
레지스터 ↔ 일반 산술 유닛들      레지스터 ↔ Tensor Core들
                                일반 산술 유닛들도 함께 존재
```

이 Volta 예에서는 FP16 입력과 FP32 누적을 사용해. 자료형과 행렬 조건에 맞는 구현을 선택해야 하며, 단순한 곱셈·덧셈 반복문을 컴파일한다고 항상 Tensor Core 명령으로 바뀌는 것은 아니야. WMMA 한 번을 물리 명령 하나나 한 사이클과 같다고 볼 수도 없어.

HBM에서는 일반적인 메모리 접근 모델을 유지하면서 공급 경로가 바뀌었고, Tensor Core에서는 지원되는 커널·명령 경로와 계산 회로가 함께 바뀌었어. 이렇게 어떤 부분이 유지되고 어떤 부분이 달라졌는지를 보아야 해. 뒤에서 따라갈 단순한 원소별 `A + B`는 여전히 일반 산술 유닛으로 설명할 수 있어.

### 언어 모델은 다음 토큰을 만들기 위해 상태를 다시 읽는다

AI 안에서도 이미지 분류나 큰 묶음의 학습만 생각하면 충분하지 않아. 언어 모델은 입력 문장을 읽은 뒤, 앞에서 만든 결과를 바탕으로 다음 토큰을 계속 생성해. 입력을 한꺼번에 처리하는 단계와 토큰을 이어 만드는 단계는 기계를 사용하는 방식이 달라.

모델의 가중치 외에도 이전 토큰에서 계산한 attention용 값을 저장해 다시 써. 이것이 **KV cache**야. CPU의 L1 같은 하드웨어 캐시 이름이 아니라, 프로그램이 재사용하려고 보관하는 데이터야. 재계산을 줄이는 대신 저장 공간과 읽기 대역폭을 사용하지. 문맥이 길고 동시 요청이 많으면 저장할 상태도 커져.

특히 작은 배치로 토큰을 생성할 때는 연산량에 비해 데이터를 많이 읽어야 할 수 있어. 모델을 여러 GPU에 나누면 중간 결과를 교환하는 시간도 생겨. 따라서 AI는 언제나 연산이 병목이라거나, 언제나 메모리가 병목이라고 단정할 수 없어. **모델, 배치 크기, 실행 단계에 따라 연산·메모리·통신의 비중이 달라지는 것**이야.

### Rubin의 숫자를 용도와 연결해보자

최신 공개 세대인 **Rubin**의 GPU 전체 구성에는 SM 224개가 있고, compute die 두 개를 NV-HBI로 연결해 하나의 GPU로 사용해. 각 다이의 SM·L2 캐시·메모리 컨트롤러가 패키지의 HBM4 메모리와 연결돼. GPU 하나가 반드시 실리콘 다이 하나인 것은 아니지만, 여러 SM과 메모리 시스템을 연결하는 원리는 이어져.

Rubin은 Tensor Core의 행렬 연산뿐 아니라 attention에서 참고 비중을 정규화하는 softmax 처리도 강화했어. 행렬 곱셈이 빨라지면 그 사이의 다른 계산이 전체 진행을 막을 수 있기 때문이야. 메모리의 공개 예비 사양은 GPU당 **최대 288 GB 용량과 22 TB/s 대역폭**이야. 용량은 가중치와 KV cache 같은 상태를 얼마나 담을 수 있는지, 대역폭은 그 데이터를 얼마나 빨리 공급할 수 있는지와 관계해.

이제 소프트웨어의 항목을 그림 속 부품에 직접 연결해보자. **attention·행렬 커널은 SM의 실행 자원을 사용하고, 가중치와 KV 버퍼는 HBM4에 보관하며, GPU 사이의 통신 요청은 GPU들을 잇는 연결망을 사용해.** 행렬 곱셈과 softmax는 서로 다른 종류의 연산이므로 커널도 그에 맞는 명령을 사용해. 전용 softmax core 하나로 attention 전체가 처리되는 것은 아니야. 버퍼를 메모리에 대응시키는 선은 데이터가 놓인 위치를, 커널을 SM에 대응시키는 선은 실행 자원을 나타내.

여러 GPU에 나눈 계산의 데이터 교환에는 NVLink 6를 사용해. **한 GPU 안의 두 다이를 잇는 NV-HBI와 GPU 사이를 잇는 NVLink는 연결하는 범위가 달라.** 연산, 저장, 데이터 이동을 함께 보아야 이런 구성이 필요한 이유를 이해할 수 있어.

이 사례는 2026-09-10 공개 예비 사양 기준이며, CUDA 13.4의 Rubin 지원은 `sm_107` 프리뷰 단계야. 위의 RTX Blackwell SM 내부 수치를 Rubin에 그대로 적용하지는 않아. 이제 하드웨어의 이런 기능을 우리가 쓰는 프로그램과 연결하는 생태계를 보자.

## 10. “좋아. 그런데 내가 SM마다 일을 직접 나눠줘야 해?” — CUDA

사용자가 이 기계를 활용할 때 모든 기능을 직접 구현할 필요는 없어. **Hugging Face Transformers → PyTorch** 경로로 모델을 실행하면, 아래로 텐서 연산 요청이 내려가. 사용할 구현은 연산 종류와 실행 조건에 따라 달라져.

자주 쓰는 계산에는 이미 최적화된 라이브러리가 있어. **cuBLAS**는 행렬 연산을 비롯한 선형대수 계산을, **cuDNN**은 합성곱이나 attention 같은 신경망 연산을 제공해. **NCCL**은 여러 GPU가 값을 모으고 나누는 통신을 담당하지. 이들을 차례로 모두 거치는 것이 아니라 필요한 연산에 맞는 구현을 사용해.

프레임워크가 가진 커널이나 직접 만든 커널을 실행할 수도 있어. CUDA C++로 작성하기도 하고, 컴파일러가 Triton 같은 형태의 코드를 생성하기도 해. CUDA 런타임과 드라이버 API는 메모리를 준비하고 GPU에 일을 제출하는 과정을 연결해. nvcc 같은 컴파일러는 실행할 코드를 만들고, Nsight Systems와 Nsight Compute는 각각 전체 실행 시간 흐름과 개별 커널의 성능을 들여다보는 도구야.

이런 라이브러리와 커널, 컴파일러, 분석 도구가 CUDA 생태계를 이루어. 하드웨어에 새 기능이 들어오면 이를 활용하는 구현도 발전해야 사용자의 코드에서 성능으로 이어져. 이제 이 큰 지도에서 **원소별 덧셈 하나를 수행하는 커널 경로**만 골라 따라가자. `A + B`가 위 라이브러리를 모두 호출한다는 뜻은 아니야.

그 경로에서 개발자는 일을 어느 정도까지 지정해야 할까?

> “GPU 안에 실행 엔진이 여러 개 있다는 건 알겠어.  
> 그럼 내가 SM 0에는 이 일을, SM 1에는 저 일을 지정해야 하나?”

CUDA는 보통 그렇게 사용하게 만들지 않아.

대신 **각 실행이 할 일과, 그 실행들을 어떻게 묶어서 얼마나 실행할지** 표현하게 해. GPU에서 실행할 프로그램과 실행 규모를 지정하는 거야. 

프로그래머가 작성하는 것은 “어느 물리적 연산기를 써라”라는 배치도가 아니라, **할 일의 구성**이야.

그리고 PyTorch를 쓰면 이 실행 설정마저 아래에 숨겨져 있어. 우리는 텐서에 대한 연산을 요청하고, PyTorch의 CUDA 구현이 GPU에서 실행할 커널을 사용해. 

이제 입장을 바꿔보자.

지금까지는 아래에서 위로 기계를 만들었어.

이번에는 우리가 쓴 코드에서 출발해서, 그 요청이 **이미 살펴본 SM과 warp까지 어떻게 내려가는지** 따라가보는 거야.

## 11. `C = A + B` 한 줄에서 시작한다

```python
import torch

A = torch.randn(1024, 1024, device="cuda")
B = torch.randn(1024, 1024, device="cuda")

C = A + B
```

GPU에 있는 두 행렬의 **같은 위치에 있는 원소끼리 더하는 것**이야. 행렬 전체를 하나의 숫자로 합치는 것이 아니라, 원소별 덧셈을 해서 같은 크기의 결과 행렬을 만드는 거지. 

```text
C[0, 0] = A[0, 0] + B[0, 0]
C[0, 1] = A[0, 1] + B[0, 1]
C[0, 2] = A[0, 2] + B[0, 2]
...
```

여기서 첫 질문을 던져.

> **“첫 번째 덧셈이 끝나야 두 번째 덧셈을 할 수 있나?”**

아니야. 각 결과를 계산하는 데 필요한 것은 그 위치의 입력 두 개뿐이야. 옆 원소의 계산 결과를 기다릴 이유가 없어.

그렇다면 백만 개가 넘는 덧셈을 순서대로 하기보다, **여러 실행에 나눠 맡기면 되겠지.**

처음에 GPU에서 발견했던 바로 그 구조야.

```text
많은 데이터가 있고
→ 각 데이터에 같은 계산을 적용하면 되고
→ 서로 다른 데이터의 계산은 병렬로 진행할 수 있다
```

## 12. GPU에 건네는 것은 “각 실행이 할 일”이다 — Kernel과 thread

CUDA에서는 GPU에서 실행할 함수를 **커널(kernel)** 로 작성하고, 그 함수를 실행하는 논리적인 인스턴스를 **thread**라고 불러. 

우리 덧셈 커널이 각 thread에 시키는 일은 이것뿐이야.

> “네가 맡은 원소 번호를 알아내.  
> A와 B에서 그 원소를 읽어.  
> 더해서 C의 같은 위치에 써.”

행렬의 원소들을 한 줄로 번호 매겼다고 생각하면:

```text
Thread 0 → C[0] = A[0] + B[0]
Thread 1 → C[1] = A[1] + B[1]
Thread 2 → C[2] = A[2] + B[2]
...
```

**서로 다른 프로그램 백만 개를 만드는 게 아니야. 같은 프로그램을 실행하면서, 각자 다른 번호의 데이터를 처리하는 거야.** 

우리가 앞에서 warp를 설명할 때 말했던 “개별 실행”이, 프로그램을 작성하는 관점에서는 바로 이 thread야.

PyTorch는 이런 원소별 연산을 위한 CUDA 커널 구현을 제공해. 다만 아래에서는 **thread 하나가 원소 하나를 처리하는 교육용 구현**을 따라가자.

실제 PyTorch 커널은 한 thread가 여러 원소를 처리하는 등의 최적화를 사용할 수 있으므로, 아래 실행 설정이 실제 `A + B`의 내부 설정과 같다는 뜻은 아니야. 

중요한 것은 구체적인 튜닝값이 아니라, **행렬에 대한 요청이 어떤 실행 구조로 표현되는지**야.

## 13. “그 프로그램을 몇 개나 실행할 건데?” — Grid와 block

우리 예제에는 `1024 × 1024 = 1,048,576`개의 출력 원소가 있어.

Thread 하나에 원소 하나를 맡긴다면, 논리적 thread도 그만큼 필요해. CUDA에서는 이 thread들을 **block으로 묶고**, 이번 커널 실행의 모든 block을 **grid**라고 불러. 

설명용으로 block 하나에 256개 thread를 넣자.

```text
Grid: 이번 덧셈에 참여하는 전체 작업

├── Block 0: Thread 256개 → 원소   0~255
├── Block 1: Thread 256개 → 원소 256~511
├── Block 2: Thread 256개 → 원소 512~767
└── ...
```

그러면 필요한 block은 4,096개야. 실행 요청은 이런 모양이 돼.

```cpp
add<<<4096, 256>>>(device_a, device_b, device_c, 1024 * 1024);
```

말로 풀면:

> “`add` 커널을 실행해.  
> Block은 4,096개이고, 각 block에는 thread가 256개야.”

이렇게 커널과 실행 규모를 지정해서 제출하는 것이 **kernel launch**야. 

그런데 모든 thread가 같은 코드를 실행한다면, 자기 원소 번호는 어떻게 알아낼까?

```cpp
__global__ void add(
    const float* a,
    const float* b,
    float* c,
    int element_count
) {
    int index = blockIdx.x * blockDim.x + threadIdx.x;

    if (index < element_count) {
        c[index] = a[index] + b[index];
    }
}
```

`blockIdx`는 내 block의 번호, `blockDim`은 block 크기, `threadIdx`는 block 안에서 내 번호야. 이것들을 조합해 담당 원소를 정하는 거지. 

예를 들어 block 번호가 3이고, 그 안에서 내 thread 번호가 10이라면:

```text
index = 3 × 256 + 10
      = 778
```

이 thread는 `A[778]`과 `B[778]`을 더해서 `C[778]`에 저장해.

`if`는 담당 원소 번호가 실제 배열 범위를 벗어나는 경우를 막아줘. 이번 예제는 원소 수가 256으로 딱 나누어떨어지지만, 일반적인 크기에서는 마지막 block에 처리할 원소가 없는 thread가 생길 수 있거든. 

여기서 `256`은 하드웨어에 고정된 block 크기가 아니야. 커널을 사용하는 쪽에서 정한 값이야. 다만 block 크기에는 장치의 상한과 커널의 자원 사용량에 따른 제약이 있어. NVIDIA GPU의 대표적인 상한인 **1024 threads/block**도 이런 사양상의 제한이지, GPU 전체에서 실행할 수 있는 thread 수가 1024개라는 뜻은 아니야. 

또 block은 단순히 번호를 붙이기 위한 묶음만은 아니야. 같은 block의 thread들은 shared memory를 공유하고 `__syncthreads()`로 동기화할 수 있어. 다만 **이번 덧셈은 서로의 중간 결과가 필요 없으므로 그런 협력 기능을 사용하지 않을 뿐**이야. 

**여기까지 정한 것은 “할 일의 구성”이야. 아직 어떤 하드웨어가 누구의 일을 맡을지는 정하지 않았어.**

## 14. “백만 개의 thread를 실행하려면 코어도 백만 개가 필요한가?” — SM에 배치하기

아니야. **논리적인 실행 수와 물리적인 연산기 수는 달라.**

여기서 앞에서 만들었던 SM이 다시 등장해.

SM은 연산 유닛뿐 아니라 레지스터, 스케줄러, shared memory 등의 자원을 갖춘 실제 실행 엔진이었지. GPU는 grid의 block들을 이 SM들에 배치해. 

예를 들면 이런 배치가 가능해.

```text
제출한 작업                    실제 실행 엔진

Block 0 ───────────────────→ SM 2
Block 1 ───────────────────→ SM 0
Block 2 ───────────────────→ SM 3
Block 3 ───────────────────→ SM 2
...
```

**Block 하나는 같은 SM에서 실행되고, SM 하나에는 자원이 허용하는 만큼 여러 block이 함께 올라갈 수 있어.**

Block 안의 thread 수를 늘려도 그 block이 여러 SM으로 나뉘지는 않아. **여러 SM에 일을 주려면 여러 block을 제출해야 해.** 이번에 준비한 4,096개 block을 GPU가 여러 SM에 나눠 맡기는 거야.

모든 block이 한꺼번에 올라가는 것은 아니야. 자리가 나면 남은 block들이 배치되고, 구체적인 배치 순서는 보장되지 않아. 

예를 들어 어떤 SM에 block 몇 개를 올렸더니, 그 SM이 보관할 수 있는 실행 상태나 레지스터 등의 자원이 찼다고 하자.

그러면 다른 block들은 다른 SM에 배치되거나 기다려야 해. 먼저 실행하던 block이 끝나서 자원이 확보되면, 그 자리에 다음 block을 배치할 수 있어. 

그러니까 GPU에 백만 개의 작업을 맡긴다는 것은, 백만 개의 물리적 코어를 요구하는 게 아니야.

**실행할 작업을 충분히 제출해두고, 실제 하드웨어가 나눠 처리하게 하는 거야.**

그리고 여기서 grid와 GPU의 차이도 분명해져.

**Grid는 이번 실행에 제출한 작업 전체이고, GPU는 그 작업을 받아 처리하는 기계야.**

Block이 4,096개라고 SM도 4,096개여야 하는 것이 아니고, grid 하나가 물리적인 GPU 부품 하나에 대응하는 것도 아니야. 

## 15. “그럼 SM은 thread를 하나씩 실행하나?” — Warp까지 내려가기

SM 하나에 배치된 block을 확대해보자.

우리 block에는 256개 thread가 있어. NVIDIA GPU는 같은 block 안의 thread를 연속된 번호 순서로 **32개씩 묶어 warp로 관리**해. 따라서 이 block에는 warp가 8개 생겨. 

```text
Block 0: 256 threads

Warp 0 → Thread   0~31
Warp 1 → Thread  32~63
Warp 2 → Thread  64~95
Warp 3 → Thread  96~127
Warp 4 → Thread 128~159
Warp 5 → Thread 160~191
Warp 6 → Thread 192~223
Warp 7 → Thread 224~255
```

이제 warp 0을 보자. 이 thread들이 해야 하는 일은 모두 같아.

```text
자기 A 값을 읽는다
→ 자기 B 값을 읽는다
→ 더한다
→ 자기 C 위치에 저장한다
```

덧셈 명령을 처리할 때는 이런 모습으로 생각하면 돼.

```text
Warp에 발행한 공통 명령: ADD

Thread 0  → A[0]  + B[0]
Thread 1  → A[1]  + B[1]
...
Thread 31 → A[31] + B[31]
```

**명령은 함께 처리하되, 각 thread의 데이터는 다른 것.**

앞에서 소개한 SIMT가, 지금 우리의 행렬 덧셈에서 실제로 나타나고 있는 거야. 

SM의 warp scheduler는 준비된 warp의 **다음 명령**을 골라 발행해. Warp 하나의 프로그램 전체를 끝내고 다음 warp로 넘어가야 하는 것은 아니야. 여러 warp의 명령 실행을 진행시키면서 연산 자원을 사용해. 

실행을 개념적으로 펼쳐보면 이런 모습이야. 아래는 실제 어셈블리나 정확한 사이클표가 아니라, 어떤 종류의 일이 진행되는지 보여주는 예시야.

```text
Warp 0: A의 담당 원소들을 읽는 명령
Warp 1: A의 담당 원소들을 읽는 명령
Warp 0: B의 담당 원소들을 읽는 명령
Warp 2: A의 담당 원소들을 읽는 명령
...
Warp 0: 준비된 값들을 더하는 명령
...
Warp 0: 결과를 C에 저장하는 명령
```

메모리 읽기·쓰기 명령은 그에 맞는 실행 경로를 사용하고, 덧셈 명령은 산술 연산 유닛을 사용해. **Warp가 특정 연산기를 계속 소유하는 것이 아니라, 명령을 실행할 때 필요한 SM의 자원을 사용하는 것**이야. 

RTX Blackwell의 compute capability 12.0에서는 SM 하나에 최대 48개 warp, 즉 1536개 논리 thread가 resident 상태로 머물 수 있어. 실제 수는 레지스터, shared memory, block 크기의 제약을 받아. 반면 FP32/INT32 연산 유닛은 SM 전체에 128개야. **Resident warp 수를 연산기 수 나누기 32로 계산하면 안 돼.** 실행 상태를 보관해 두고 여러 warp의 명령이 같은 자원을 사용하는 거지.

Warp 폭 32, 특정 명령의 처리율, 결과가 준비되기까지의 지연은 서로 다른 개념이야. 유닛 수만 보고 명령이 한 사이클에 끝난다고 해석할 수도 없어.

여기서 `A + B` 한 줄이 드디어 실제 하드웨어 동작까지 내려온 거야.

> **전체로 보면 행렬 덧셈이고,  
> thread 하나가 보면 자기 원소의 덧셈이고,  
> SM이 보면 warp에 발행하는 읽기·덧셈·쓰기 명령들이야.**

## 16. 각자의 결과를 써놓으면, 행렬 덧셈이 끝난다

우리 덧셈 커널에서는 각 thread가 자기 원소를 계산해서 GPU 메모리의 `C`에 써.

```text
Thread 0 → C[0]에 저장
Thread 1 → C[1]에 저장
Thread 2 → C[2]에 저장
...
```

서로 다른 thread가 서로 다른 출력 위치를 담당하니까, CPU가 각 SM의 결과 조각을 받아서 다시 행렬로 조립할 필요는 없어. 모든 작업이 끝나면 결과는 이미 `C`의 각 위치에 들어 있어.

다만 여기서 “끝났다”는 말에는 두 시점이 있다는 것을 구분해야 해.

```python
C = A + B
```

이 호출이 반환되는 시점과 GPU가 실제 덧셈을 모두 끝낸 시점은 같지 않을 수 있어. PyTorch의 GPU 연산은 기본적으로 **비동기적으로 제출**되기 때문이야. CPU는 작업을 제출한 뒤 다음 일을 진행할 수 있어. 

같은 CUDA stream에 다음 GPU 작업을 제출하면, 그 작업은 앞선 작업 뒤에 실행되도록 순서가 유지돼. 따라서 그다음 연산이 `C`를 사용한다고 해서, 매번 CPU가 직접 계산 완료를 기다려야 하는 것은 아니야. 

반면 CPU에서 결과를 읽어야 하거나, GPU 계산 시간을 정확히 재려고 하는 등의 상황에서는 필요한 동기화가 있어야 해. **“실행 요청을 제출했다”와 “계산이 완료됐다”는 다른 사건**인 거지. 

---

이제 처음부터 끝까지 하나의 요청으로 연결해보자.

```text
PyTorch
“C = A + B를 계산해줘.”
        ↓
CUDA 커널 구현
“각 thread가 자기 원소 두 개를 읽고 더해서 저장하게 하자.”
        ↓
Kernel launch
“이 커널을 4,096개 block,
 block마다 256개 thread로 실행해.”
        ↓
GPU의 작업 배치
“이 block은 이 SM이 맡아.”
        ↓
SM의 warp scheduler
“이 warp의 다음 명령을 실행해.”
        ↓
SM 내부의 연산·메모리 유닛
실제 값을 읽고, 더하고, 결과를 쓴다.
        ↓
GPU 메모리의 C에 결과가 완성된다.
```

여기서 **grid와 block은 제출한 작업의 구조**, **thread는 프로그램의 논리적인 실행**, **warp는 그 실행들을 묶어 명령을 처리하는 단위**, **SM은 그 일을 실제로 수행하는 하드웨어**야. 

그리고 이 이야기는 처음의 삼각형 두 개로 돌아가.

예전에는 이렇게 말해야 했어.

> “이 사각형을 그려줘.  
> 그런데 각 위치의 색은 A와 B의 값을 더해서 정해줘.”

이제는 이렇게 말하면 돼.

```python
C = A + B
```

**계속 같았던 것은 ‘많은 데이터에 같은 계산을 적용한다’는 일이야. 달라진 것은, 그 일을 직접 표현하는 방법과 실행하는 하드웨어가 함께 발전했다는 점이지.**

더 다양한 표면을 그리려는 요구는 프로그래머블 셰이더로, 일반 배열을 계산하고 협력하려는 요구는 CUDA와 이를 지원하는 프로세서로 이어졌어. 이후 행렬 연산과 큰 모델의 상태, GPU 사이 데이터 교환이 중요해지면서 연산기와 메모리, 연결망도 발전했지. 라이브러리와 프레임워크는 그 기능을 우리가 쓰는 한 줄과 연결해. 오늘 본 thread와 block, warp와 SM은 그 한 줄이 실제 기계에서 실행되는 과정을 이해하는 언어야.

# 선택형 부록: GPU 밖으로 넓혀보는 이야기

본문에서는 NVIDIA GPU로 `A + B`가 실행되는 과정을 따라갔어. 여기부터는 궁금한 주제를 골라 더 볼 수 있는 부록이야. 다른 가속기, LLM을 돌리는 데이터센터, 숫자와 메모리, 운영체제와 배포까지 같은 질문으로 살펴보자. **어떤 일이 병목이 됐고, 소프트웨어와 하드웨어가 각각 어떻게 대응했을까?**

## A. NVIDIA 말고 다른 회사들은 무엇을 만들었을까?

### A.1. AMD도 GPU와 계산 플랫폼을 함께 만들고 있었어

AMD도 그래픽 GPU를 범용 계산에 사용해왔어. 2017년 Radeon Instinct에는 ROCm 소프트웨어를 함께 제공했고, 2020년 CDNA에서는 기존 스칼라·벡터 실행 자원에 행렬 연산부를 더했어. 그래픽에 집중하는 Radeon의 RDNA와 AI·HPC 계산에 집중하는 Instinct의 CDNA가 갈라진 거지. 이 연도들은 몇 가지 이정표이고, AMD의 GPU 계산이나 ROCm이 그때 처음 시작됐다는 뜻은 아니야.

계산 칩렛과 HBM을 묶은 하드웨어만으로 CUDA의 대안이 완성되지는 않아. 프레임워크가 쓸 라이브러리와 커널, 컴파일러, 런타임, 분석 도구가 함께 필요해. **ROCm은 AMD GPU를 실제 프로그램에서 사용하게 만드는 플랫폼**이고, HIP는 그 안에서 커널 소스를 다루는 한 부분이야.

출처: [AMD CDNA 백서](https://www.amd.com/content/dam/amd/en/documents/instinct-business-docs/white-papers/amd-cdna-white-paper.pdf), [AMD CDNA 아키텍처](https://www.amd.com/en/technologies/cdna.html).

### A.2. HIP는 CUDA 실행 파일을 그대로 돌리는 마법은 아니야

HIP는 Heterogeneous-compute Interface for Portability의 약자야. GPU 커널을 작성하는 C++ 언어 기능과, 메모리 할당·복사·실행을 제어하는 호스트 API를 제공해. CUDA C++와 닮아 있어서 HIPIFY로 많은 호출을 변환할 수 있어. 부록의 그림은 `CUDA 소스 → HIP 소스로 이식 → AMD용 컴파일 → ROCm 런타임 → AMD GPU`라는 경로야.

여기서 옮기는 것은 **소스 코드**야. 이미 만들어진 CUDA 바이너리가 AMD에서 그대로 실행된다는 뜻은 아니지. 지원하지 않는 기능과 라이브러리를 바꾸고, 다시 빌드하고, 계산이 맞는지 확인해야 해. 실행되더라도 하드웨어의 자원 배치가 다르니 성능 튜닝은 다시 필요할 수 있어. 프레임워크가 이 차이를 가려주기도 하지만, 직접 작성한 CUDA 커널이 있으면 이식 작업이 사용자에게 드러나.

출처: [AMD — What is HIP?](https://rocm.docs.amd.com/projects/HIP/en/latest/what_is_hip.html).

### A.3. TPU는 신경망 계산에서 출발한 기계야

Google의 TPU, Tensor Processing Unit은 머신러닝을 위해 만든 전용 프로세서야. 초기에는 대규모 서비스의 추론 지연시간과 전력 비용이 중요한 문제였고, 이후 학습과 여러 칩을 묶는 시스템으로 확장했어. 행렬 실행부에서는 곱셈·누산 회로 사이로 값을 흘려보내며 재사용해. 이런 행렬 배열 외에도 메모리, 버퍼, 제어와 다른 종류의 연산 자원이 필요해.

소프트웨어의 대표 경로는 **JAX의 배열 계산과 분할 지정 → XLA의 컴파일·분할 → TPU 런타임과 실제 칩**이야. PyTorch 연동도 있고, XLA는 GPU도 대상으로 삼아. 특정 언어가 어느 칩에 독점이라는 구분보다 출발점이 중요해. GPU는 그래픽에서 범용 커널 실행으로 넓어졌고, TPU는 텐서 계산·컴파일러·분산 실행을 중심으로 발전한 거야.

출처: [Google의 초기 TPU 논문](https://research.google/pubs/in-datacenter-performance-analysis-of-a-tensor-processing-unit/), [Cloud TPU 아키텍처](https://docs.cloud.google.com/tpu/docs/system-architecture-tpu-vm), [JAX AI 스택](https://docs.cloud.google.com/tpu/docs/jax-ai-stack).

### A.3.1. Torch/XLA는 익숙한 tensor 호출을 TPU용 그래프로 모아

PyTorch/XLA의 전통적인 lazy tensor 경로에서는 `relu(x @ w + b)` 같은 연산을 그래프에 기록해. 실행 경계나 결과가 필요한 시점에 XLA가 그 계산을 컴파일하고, 런타임이 TPU에 제출해. 컴파일러는 연산 결합과 데이터 배치, 버퍼 사용을 정해서 행렬·벡터 실행부를 활용하게 해. 같은 조건의 그래프는 컴파일 결과를 재사용하지만, 입력 모양이나 그래프가 바뀌면 새 컴파일이 필요할 수 있어.

이 과정은 PJRT 이전에도 있었어. **그래프로 계산을 표현하는 방식과 장치에 일을 요청하는 방식은 별개**야. 이 부록은 전통적인 경로를 설명하며, 모든 PyTorch·TPU 실행을 한 가지로 일반화하지 않아. 2026년에는 더 네이티브한 PyTorch 통합을 지향하는 TorchTPU도 발표됐어.

출처: [PyTorch/XLA 2.4 — XLA Tensor Deep Dive](https://docs.pytorch.org/xla/release/r2.4/index.html), [Google — TorchTPU 발표](https://developers.googleblog.com/torchtpu-running-pytorch-natively-on-tpus-at-google-scale/).

### A.3.2. XRT에서 PJRT로: 장치를 부르는 경계를 바꿨어

이전 XRT는 TensorFlow 기반 서비스였어. PyTorch/XLA가 gRPC 요청을 보내 컴파일과 장치 실행을 사용했으니, 서비스 설정과 요청 처리의 부담이 있었지. PJRT 전환 후에는 JAX도 사용하는 장치 API를 통해 TPU용 `libtpu` 구현에 접근해. PyTorch/XLA 2.0에서 기존 XRT 설정이 없을 때 기본 선택이 됐고, 2.1에서 안정화됐어.

PJRT는 장치 탐색, 버퍼, 컴파일·로드, 실행과 완료를 다루는 인터페이스야. **장치별 구현을 같은 API 뒤에 연결할 수 있게 하는 것**이지, XLA 컴파일러나 TPU 하드웨어를 대체하는 것은 아니야. 이 전환으로 gRPC 경로의 부담과 설정을 줄였지만, 여러 TPU 호스트 사이의 통신·동기화는 여전히 필요해.

출처: [PyTorch/XLA — XRT에서 PJRT로의 전환](https://docs.pytorch.org/xla/release/r2.4/runtime.html), [OpenXLA — PJRT](https://openxla.org/xla/pjrt), [PJRT API 역할](https://openxla.org/xla/pjrt/cpp_api_overview).

### A.3.3. HLO/MHLO에서 StableHLO로: 계산 표현에도 호환성 계약이 필요했어

장치 실행 경계와 별개로, 컴파일러에 넘길 계산을 어떻게 저장하고 교환할지도 문제였어. HLO와 MLIR 기반 MHLO는 계산을 표현했지만, 버전이 달라져도 오래 교환할 수 있다는 계약은 없었어. StableHLO는 연산의 의미와 직렬화·버전 호환성을 정한 표현이고, 2024년 상반기에 1.0이 나왔어. PyTorch export와 PyTorch/XLA를 통해 만들 수 있으며, JAX·TensorFlow도 생산자가 되고 XLA 이외의 컴파일러도 소비자가 될 수 있어.

**StableHLO는 ‘무엇을 계산하는가’, PJRT는 ‘장치에 컴파일과 실행을 어떻게 요청하는가’를 담당해.** StableHLO 프로그램을 PJRT 컴파일 요청의 입력으로 전달하는 경로도 있으므로, 둘을 경쟁하는 런타임이나 단순한 앞뒤 세대로 보면 안 돼. XLA는 여전히 내부 HLO로 최적화하고 장치용 코드를 생성해.

안정된 계산 표현은 TPU 기계어가 아니고, 모델 가중치를 모두 포함하는 패키지라는 뜻도 아니야. 호환성 보장은 정해진 직렬화 API와 의미론의 범위에 적용돼. 컴파일러의 지원 연산, 장치에 종속된 custom call, 실제 성능과 수치 차이는 따로 확인해야 해. 그래도 프레임워크와 장치가 서로의 내부 구현을 매번 따라 바꾸는 부담을 줄이는 기반이 돼.

출처: [OpenXLA 2022 포스터 — 기존 HLO/MHLO의 문제](https://pytorch.s3.amazonaws.com/posters/ptc2022/H01.pdf), [StableHLO 개요](https://openxla.org/stablehlo), [로드맵과 1.0](https://openxla.org/stablehlo/roadmap), [호환성 범위](https://openxla.org/stablehlo/compatibility), [Torch Export to StableHLO](https://docs.pytorch.org/xla/release/r2.6/features/stablehlo.html).

### A.4. NPU 스타트업은 칩과 함께 추론 서비스를 만들고 있어

NPU는 Neural Processing Unit이라는 넓은 이름이야. 모두 같은 구조도 아니고 모두 추론 전용인 것도 아니야. 여기서는 데이터센터 추론에 집중하는 예로 FuriosaAI와 Rebellions를 보자. Furiosa는 RNGD와 컴파일러·서빙 엔진을, Rebellions는 NPU와 RBLN 컴파일러·프레임워크 연동을 함께 만들어. 목표는 요구 지연시간을 지키면서 같은 서비스를 더 적은 전력과 비용으로 제공하는 거야.

새로운 모델이 나오면 행렬 곱셈만 지원한다고 끝나지 않아. 모델의 연산과 텐서 모양, 숫자 형식, KV 관리와 요청 스케줄까지 따라가야 해. **실제 모델을 실행하는 소프트웨어가 준비돼야 전용 회로도 쓸모가 있어.** 그래서 칩의 최대 연산량보다, 필요한 모델을 어떤 품질·지연시간·처리량으로 서비스할 수 있는지 함께 봐야 해.

출처: [Furiosa SDK 2026.2](https://furiosa.ai/blog/furiosa-sdk-2026-2), [Rebellions Inference Platform](https://rebellions.ai/rebellions-product/rebellions-inference-platform/).

### A.5. Cerebras는 웨이퍼를 잘라 생기는 경계까지 연결했어

슬라이드 왼쪽의 [Cerebras 공식 사진](https://www.cerebras.ai/chip)에서 사람의 손과 웨이퍼 크기를 비교해봐. 사진은 물리적 크기를 보여주고, 오른쪽 도식은 그 공간에 계산과 메모리를 어떻게 배치하는지 보여줘.

보통 웨이퍼에는 여러 칩을 만들고, 이를 잘라 각각 패키징해. Cerebras는 웨이퍼 규모의 연결망에 계산 코어와 가까운 SRAM을 반복 배치하는 방향을 택했어. 2024년 WSE-3는 90만 개 AI 계산 코어와 44 GB의 칩 내부 SRAM을 가진 예야. 이 코어를 NVIDIA의 CUDA core와 일대일로 비교할 수는 없고, SRAM도 GPU 옆에 놓이는 HBM과 종류와 위치가 달라.

컴파일러는 모델의 계산을 이 거대한 공간에 배치해. 그렇다고 모든 모델의 가중치가 언제나 웨이퍼 안에 들어가는 것은 아니야. 큰 모델의 학습에는 외부 MemoryX에서 가중치를 흘려보내는 방식도 있어. **계산과 저장을 가깝게 놓는 선택을 극단까지 밀어붙인 것**이지, 외부 용량과 입출력·전력·냉각 문제가 사라진 것은 아니야.

출처: [Cerebras WSE-3 발표](https://www.cerebras.ai/press-release/cerebras-announces-third-generation-wafer-scale-engine), [PyTorch 모델의 웨이퍼 배치](https://www.cerebras.ai/blog/supporting-pytorch-on-the-cerebras-wafer-scale-engine), [Weight streaming 실행 방식](https://training-api.cerebras.ai/en/1.9.1/wsc/cerebras-basics/cerebras-execution-modes.html).

## B. LLM은 GPU와 데이터센터를 어떻게 쓰고 있을까?

### B.1. 학습 메모리에는 가중치 말고도 많이 들어가

LLM 학습은 forward로 예측과 손실을 계산하고, backward로 gradient를 구한 뒤, optimizer가 가중치를 갱신하는 과정이야. 같은 GPU의 실행 자원을 쓰지만 단계마다 필요한 커널은 달라. HBM에는 가중치뿐 아니라 중간 activation, gradient, optimizer의 이력 상태도 필요해. 정확한 양은 숫자 형식과 optimizer, 구현 방식에 따라 달라져.

ZeRO 같은 방법은 상태를 여러 GPU에 나눠 담아 중복을 줄여. Activation을 저장하는 대신 나중에 다시 계산하면 메모리를 아끼는 대신 계산 시간이 늘 수 있어. 그래서 **모델 파일이 GPU 메모리에 들어간다는 것과 그 모델을 학습할 수 있다는 것은 다른 조건**이야. 더 큰 학습은 저장할 상태, 다시 계산할 값, 다른 GPU에서 가져올 값을 함께 결정하는 일이 돼.

출처: [ZeRO: Memory Optimizations Toward Training Trillion Parameter Models](https://arxiv.org/abs/1910.02054).

### B.2. LLM 서비스는 토큰과 KV 메모리를 함께 스케줄해

서비스에는 길이가 다른 요청이 계속 들어와. 완료된 요청을 빼고 새 요청을 batch에 넣으면 GPU에 일을 계속 공급할 수 있어. 긴 입력의 prefill을 작은 조각으로 나누면 이미 답변 중인 요청이 다음 decode를 위해 오래 기다리는 일을 줄일 수 있지. 부록의 그림은 A가 끝난 자리에 C가 들어오는 두 반복을 보여줘.

여러 요청을 묶으면 가중치를 읽어 더 많은 토큰 계산에 재사용할 수 있지만, 살아 있는 요청의 KV 상태도 더 많이 필요해. vLLM과 TensorRT-LLM 같은 실행기는 토큰 배치와 메모리 관리를 함께 다뤄. **첫 토큰까지의 시간, 토큰 사이 간격, 전체 처리량, 메모리 사용량이 서로 연결돼 있는 것**이야. KV는 소프트웨어가 HBM 등에 보관하는 상태이며, 최적의 batch나 병목은 모델·문맥 길이·하드웨어에 따라 달라져.

출처: [PagedAttention / vLLM 논문](https://arxiv.org/abs/2309.06180), [TensorRT-LLM의 chunked prefill](https://developer.nvidia.com/blog/streamlining-ai-inference-performance-and-deployment-with-nvidia-tensorrt-llm-chunked-prefill/).

### B.3. 모델을 나누는 방법이 통신의 모양을 정해

Data parallel은 서로 다른 샘플을 처리하고 gradient를 합쳐 갱신을 맞추는 방식이야. 상태를 여러 장치에 나눠 담는 방법도 결합할 수 있어. Tensor parallel은 행렬 같은 tensor 자체를 나누므로, 층 안에서도 부분 결과를 자주 합치거나 교환해야 해.

Pipeline parallel은 서로 다른 층을 GPU들에 배치해. Forward의 activation은 다음 단계로, backward의 gradient는 이전 단계로 전달돼. 작은 묶음을 연속으로 흘려도 앞뒤 단계를 기다리는 빈 시간이 생길 수 있어. 실제 큰 모델은 이런 방법을 조합하고, 더 긴 문맥을 나누는 방법도 사용해.

중요한 것은 **논리적인 분할을 물리 연결에 맞추는 일**이야. 자주 통신하는 계산을 느린 연결 너머에 놓으면 GPU를 늘려도 기다리는 시간이 커져. 메모리에 들어가는지만 보지 말고, 어떤 데이터가 어느 연결을 얼마나 자주 건너는지도 봐야 해.

출처: [Llama 3 논문 §3.3.2 — 병렬화와 네트워크 배치](https://arxiv.org/html/2407.21783v3#S3.SS3.SSS2).

### B.4. 한 장이 느려져도 수많은 GPU가 기다릴 수 있어

동기식 학습에서는 같은 집단 통신에 참여하는 GPU 하나가 느려져도 다른 GPU들이 기다릴 수 있어. 고장이 나면 저장한 학습 상태에서 복구해야 하고, 상태를 자주 저장하면 잃는 계산은 줄지만 스토리지 쓰기 부하가 커져. 계산 성능만 높여서는 해결되지 않는 문제들이야.

Llama 3 논문에는 이런 운영 경험이 실제로 나와. 온도가 동작 속도에 영향을 주고, 많은 GPU가 동시에 계산을 시작하거나 통신·저장을 기다리면 데이터센터 전력 사용량도 함께 출렁여. **유효한 학습 시간은 네트워크·스토리지·장애 복구·전력·냉각이 함께 결정해.** GPU 대수가 커질수록 부품 하나의 문제를 빨리 찾고 복구하는 소프트웨어가 중요해지는 이유야.

출처: [Llama 3 논문 §3.3.1, §3.3.4 — 인프라와 운영 문제](https://arxiv.org/html/2407.21783v3#S3.SS3.SSS4).

### B.5. NVIDIA가 네트워킹까지 하는 이유도 GPU의 대기 시간이야

GPU 사이에 데이터가 늦게 도착하면 비싼 연산기가 기다려. NVLink와 NVSwitch는 서버나 랙 규모의 긴밀한 GPU 연결 영역을 만들고, ConnectX 같은 어댑터와 InfiniBand 또는 Ethernet 스위치는 이런 영역들을 더 넓게 연결해. NVIDIA는 2020년에 Mellanox 인수를 마치면서 네트워킹 제품군과 기술을 함께 갖추게 됐어. 모든 기술을 처음부터 NVIDIA 혼자 만든 이야기는 아니야.

소프트웨어 쪽의 **NCCL은 tensor를 합치고 모으는 집단 통신 라이브러리**야. AllReduce·AllGather·ReduceScatter 같은 요청을 실제 연결에 맞춰 수행해. NCCL 자체가 InfiniBand 같은 네트워크 방식이나 스위치 칩은 아니지. BlueField DPU는 네트워크·스토리지 등 인프라 처리를 맡는 다른 역할이고, 모든 GPU 통신이 무조건 이를 거치는 것도 아니야. 이제 플랫폼의 범위가 개별 GPU의 실행에서 GPU 사이의 이동까지 넓어진 거야.

출처: [NCCL 개요](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html), [NVIDIA 네트워킹](https://www.nvidia.com/en-us/networking/), [2020년 Mellanox 인수 완료](https://nvidianews.nvidia.com/news/nvidia-completes-acquisition-of-mellanox-creating-major-force-driving-next-gen-data-centers).

## C. 숫자를 줄이고, 이동을 줄이고, 더 가까이 연결하기

### C.1. 같은 16비트라도 범위와 정밀도는 다르게 살 수 있어

부동소수점은 부호·지수·소수부에 비트를 나눠 써. 지수는 주로 표현 범위를, 소수부는 같은 크기 근처의 값을 얼마나 촘촘하게 표현할지를 정해. FP32는 이 배분이 `1 / 8 / 23`, FP16은 `1 / 5 / 10`, BF16은 `1 / 8 / 7`이야. 그래서 둘 다 16비트인 FP16과 BF16도 같은 선택이 아니야. BF16은 FP32의 지수 범위를 유지하고, FP16은 소수부에 더 많은 비트를 써.

정밀한 수치 계산에는 FP64, 오차에 민감한 계산에는 FP32가 계속 필요해. 한편 TF32는 별도의 작은 tensor 저장 형식으로 이해하면 안 돼. **FP32로 저장한 입력을 Tensor Core 곱셈 전에 반올림하고 FP32로 누적하는 계산 모드**야. 저장할 때의 형식, 곱셈에서 쓰는 정밀도, 누적 정밀도를 구분해야 숫자 이름들이 덜 헷갈려.

출처: [NVIDIA Transformer Engine의 형식 비교](https://docs.nvidia.com/deeplearning/transformer-engine/user-guide/features/low_precision_training/introduction/introduction.html), [TF32 내부 동작](https://developer.nvidia.com/blog/accelerating-ai-training-with-tf32-tensor-cores/).

### C.2. 최근의 방향은 모든 계산을 4비트로 만드는 것이 아니야

FP8·FP4·INT8·INT4 같은 방식은 값을 더 작게 저장하고 움직이려는 선택이야. 지원하는 행렬 회로에서는 처리량도 높일 수 있어. 대신 표현 범위와 반올림 오차를 다뤄야 하므로, tensor 전체나 작은 값 묶음에 맞는 스케일을 정하고 값과 함께 보관해. 따라서 값의 비트 수를 반으로 줄였다고 전체 모델 메모리도 언제나 정확히 반이 되는 것은 아니야.

FP 계열은 부동소수점 표현이고 INT 계열은 정수 코드와 스케일을 사용하는 양자화야. 누적과 민감한 연산은 더 넓게 유지할 수 있고, 학습에서는 작은 업데이트가 사라지지 않도록 FP32 상태를 남기기도 해. **낮은 정밀도의 피연산자와 필요한 곳의 높은 정밀도를 조합하고, 실제 모델 품질을 검증하는 것**이 혼합 정밀도의 방향이야. 형식 이름만이 아니라 스케일 방식·하드웨어·커널이 함께 맞아야 해.

출처: [Transformer Engine — FP8·FP4와 스케일링](https://docs.nvidia.com/deeplearning/transformer-engine/user-guide/examples/fp8_primer.html), [Mixed Precision Training 논문](https://arxiv.org/abs/1710.03740).

### C.3. HBM은 초당 옮길 수 있는 바이트를 늘려

우리 FP32 `A + B`를 다시 보자. 입력 두 개를 각각 한 번 읽고 출력 하나를 한 번 쓰면, 덧셈 한 번에 12바이트를 옮겨야 해. 이 트래픽이 외부 메모리까지 간다고 가정하고 초당 4 TB를 지속해서 공급할 수 있다면, 이상적인 상한은 `4 × 10^12 / 12 ≈ 0.33 × 10^12`번의 덧셈이야. **이 작업의 대역폭 상한은 약 0.33 TFLOP/s**인 셈이지. 실제 제품의 측정값이나 GPU의 최고 계산 성능을 말하는 것은 아니야.

HBM은 메모리를 여러 층으로 쌓고 GPU 가까이 놓아 많은 짧은 병렬 배선으로 연결해. 예를 들어 HBM3E의 스택당 데이터 인터페이스는 1024비트야. 많이 담는 용량, 한 번 읽을 때의 지연, 초당 공급하는 대역폭은 서로 다른 개념이야. HBM으로 공급 경로를 넓혀도 같은 값을 계속 다시 읽으면 부담이 남으니, 소프트웨어가 가져온 값을 가까이서 재사용하는 것도 중요해.

출처: [Micron HBM3E 인터페이스](https://www.micron.com/products/memory/hbm/hbm3e), [NVIDIA — Inside Pascal의 HBM 구성](https://developer.nvidia.com/blog/inside-pascal/). 위 덧셈 상한은 캐시 재사용과 추가 오버헤드를 제외한 설명용 계산이야.

### C.4. FlashAttention은 거대한 중간 행렬을 메모리에 쓰지 않게 바꿨어

Dense attention은 `O = softmax(QKᵀ / √d)V`로 쓸 수 있어. 이를 별도 연산들로 실행하면 Q와 K의 곱으로 만든 점수 행렬을 HBM에 쓰고, softmax가 다시 읽은 뒤 확률 행렬을 또 쓰게 돼. 토큰이 N개이면 이 중간 행렬은 `N × N`이야. 연산을 빨리 하는 것만큼 이 큰 배열을 오가는 비용이 문제가 돼.

FlashAttention은 작은 타일을 SM의 shared memory·레지스터 같은 가까운 저장 공간에 가져와 계산해. 행별 최댓값·합·출력의 중간 상태를 갱신하며 softmax를 이어 계산하므로, 전체 점수와 확률 행렬을 HBM에 통째로 만들 필요가 없어. **GPU의 메모리 계층에 맞춰 알고리즘의 평가 순서를 바꾼 것**이야.

기본 FlashAttention은 attention을 희소화하거나 근사한 방법이 아니야. 같은 dense attention을 계산하지만 순서가 달라 부동소수점 반올림 결과는 달라질 수 있어. 전체 연산량이 여전히 문맥 길이의 제곱으로 커진다는 점도 남아. 이름에 “빠르다”가 붙었다고 모든 비용이 사라진 것은 아니지.

출처: [FlashAttention 논문 — Figure 1, Algorithm 1](https://arxiv.org/abs/2205.14135).

### C.5. TSMC의 패키징은 여러 부품을 하나의 계산기로 만드는 일이야

계산 다이와 HBM을 가깝게 놓으려면 미세한 배선을 연결하고, 전원을 공급하고, 열도 빼야 해. CoWoS는 이 부품들을 한 패키지에 통합하는 기술이야. 그림의 CoWoS-S는 실리콘 interposer를 쓰고, CoWoS-R은 재배선층을, CoWoS-L은 재배선층과 국소 실리콘 연결을 사용해. CoWoS 전체를 언제나 하나의 거대한 실리콘 interposer라고 생각하면 안 돼.

SoIC는 별도의 다이들을 촘촘한 접합으로 수직 연결하는 기술이야. HBM 안의 DRAM 층을 잇는 TSV 적층과 구분해야 하고, CoWoS와 결합할 수도 있어. 정상인 다이를 골라 조립해도 접합 수율·발열·전력·패키지 크기의 제약은 남아. **트랜지스터를 작게 만드는 것과 함께, 계산·메모리·연결을 물리적으로 조립하는 방법도 아키텍처의 일부가 된 것**이야.

출처: [TSMC CoWoS-S/R/L](https://3dfabric.tsmc.com/english/dedicatedFoundry/technology/cowos.htm), [TSMC SoIC](https://3dfabric.tsmc.com/english/dedicatedFoundry/technology/SoIC.htm).

## D. 좋은 칩을 실제 운영체제와 서비스에서 쓰기까지

### D.1. 토발즈의 불만은 Linux 지원과 협력의 문제였어

유명한 장면은 2012년 Aalto 대학 대담에서 나왔어. 한 사용자가 Optimus 노트북 그래픽을 Linux에서 쓰기 어려웠던 경험을 물었고, 토발즈는 NVIDIA의 Linux 지원과 커뮤니티 협력을 강하게 비판했어. GPU가 빠른지와 별개로, 운영체제에 통합하고 문제를 함께 고칠 수 있는지가 중요한 거야. 이 사건을 지금도 같은 개인적 감정이 이어진다는 이야기로 넓힐 필요는 없어.

이후 NVIDIA는 2022년 R515에서 GPU 커널 모듈의 소스를 공개했고, 2024년 R560에서는 지원되는 GPU의 기본 선택을 그쪽으로 옮겼어. **공개된 층은 커널 모듈**이고, 사용자 공간 드라이버와 펌웨어는 별도 구성 요소로 남아 있어. 소스 공개가 전체 CUDA 스택의 공개나 Linux 본류 통합과 같은 사건은 아니야. 하드웨어를 쓰게 하는 플랫폼은 운영체제와 유지보수의 경계까지 포함해.

출처: [Aalto — Linus Torvalds 대담](https://www.youtube.com/watch?v=MShbP3OpASA&t=2900s), [2022년 커널 모듈 공개](https://developer.nvidia.com/blog/nvidia-releases-open-source-gpu-kernel-modules/), [2024년 기본 선택 전환](https://developer.nvidia.com/blog/nvidia-transitions-fully-towards-open-source-gpu-kernel-modules/).

### D.2. Docker에서 GPU를 쓰면 애플리케이션 환경째로 옮길 수 있어

GPU 프로그램은 Python 패키지, 프레임워크, CUDA 라이브러리와 사용자 공간의 여러 의존성이 맞아야 해. 이를 컨테이너 이미지 하나에 묶으면 개발 머신에서 맞춘 환경을 호환되는 클러스터에서도 실행할 수 있어. 작업마다 필요한 버전이 달라도 호스트 전체를 그 환경으로 다시 설치할 필요가 줄고, 이미지 버전을 기준으로 재현과 배포를 관리할 수 있지.

이것이 **애플리케이션 환경을 포장하면서 실제 GPU 가속까지 가져가는 의미**야. 호스트에는 호환되는 GPU와 드라이버, GPU 접근을 구성한 컨테이너 실행 환경이 필요해. 이미지가 하드웨어까지 담는 것은 아니므로, CPU 아키텍처와 필요한 GPU 기능도 맞아야 해. 같은 이미지가 모든 GPU에서 같은 속도나 비트 단위로 같은 수치 결과를 보장하는 것도 아니야.

출처: [NVIDIA Container Toolkit — Concepts](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.10.0/concepts.html), [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/why-cuda-compatibility.html).

### D.3. 컨테이너 안의 프로그램도 호스트 드라이버를 통해 GPU에 닿아

일반적인 Linux GPU 컨테이너는 자기 애플리케이션과 CUDA 런타임을 갖지만, Linux 커널과 GPU 커널 드라이버는 호스트의 것을 사용해. Container Toolkit과 CDI 같은 연결 장치가 선택된 GPU의 장치 파일과 필요한 드라이버 라이브러리에 접근하도록 환경을 구성해. **GPU를 소프트웨어로 흉내 내는 대신 실제 장치에 작업을 제출하는 것**이야.

그래서 호스트 드라이버와 컨테이너가 요구하는 CUDA 조건은 여전히 맞아야 해. 컨테이너 수만큼 물리 GPU가 생기는 것도 아니고, 같은 GPU를 공유하면 메모리와 계산 자원을 두고 경쟁할 수 있어. 장치 접근을 열어주는 것, 자원을 나눠 쓰는 것, 강한 하드웨어 분할을 제공하는 것은 각각 다른 문제야. 이 경계를 이어줬기 때문에 환경은 이미지로 배포하면서 계산은 실제 GPU에 맡길 수 있게 된 거지.

출처: [NVIDIA Container Toolkit 아키텍처](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/arch-overview.html), [CDI 지원](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/cdi-support.html).
